# Content continuity and information fidelity

## Principle

UI Spec Studio accumulates professional design knowledge. Preserve still-valid
behavior, reasoning conditions, exceptions, examples and verification requirements
before shortening or reorganizing prose. A word budget, a preferred paragraph
length or a number of reference files does **not** decide whether a capability
remains. Text economy is a subordinate editing goal.

The portable skill is what a consuming agent receives. Its required references
and any conditionally linked specialty material must actually be part of the
installed package. Moving a detailed rule into a maintainer-only README or
review report does not preserve runtime guidance.

## Historical comparison procedure

1. Compare actual release-tag files, not just changelogs, headings or topic names.
   Record file additions, deletions, splits, moves, byte counts and changed
   responsibility boundaries. Use the old source's exact tag and path.
2. Segment affected sections by **design problem**, **applicable condition**,
   **professional cause or relationship**, **action**, **choice among variants**,
   **failure/reversal case**, and **verification outcome**.
3. Look for the operative rule in the complete installed skill. Distinguish exact
   retention, equivalent rewriting, a justified replacement, a relocation with
   the correct reading contract, and loss or weakened specificity. A missing
   heading may be a harmless rename; a present keyword can hide lost meaning.
4. Record the reason for each nontrivial deletion. Accept correction of a
   demonstrated error, a real conflict, redundant wording *with the same
   substantive conditions*, or a complete and better replacement. If the source
   remains valid and independent, retain it or reorganize without information
   loss. Reassess linked examples and cross-references after the change.
5. Restore unjustifiably lost guidance in its responsible reference, integrating
   subsequent discoveries instead of rolling the whole file backward. Preserve
   current correct methods and define which historical detail changes a decision.
6. Exercise relevant decision scenarios with the current skill: open brief versus
   accepted direction; concrete source demo versus a copied description; strong
   art direction versus routine control; static frame versus continuous motion;
   component trial versus assembled application; and assertion pass versus
   actually viewed UI. Record precisely which work and evidence ran.
7. Re-run structure, link, package, installation, multi-platform and browser
   checks. Verify the **published tag and downloaded artifact** independently.
   Reading references completely and agent decision quality still require their
   own evidence; successful tests do not certify them automatically.

## Evolution rule

**Accepted professional knowledge + new findings → larger or better-organized
capability, not forced replacement inside a fixed budget.**

When the combined required references grow, prefer responsible separation,
progressive specialized reading and clear cross-links. Use host-appropriate
complete chunked reads when needed. Keep the default required foundation
coherent; do not assume every optional research source must always be loaded.
Do not introduce a new arbitrary byte, line or token ceiling to replace an old
one.

An instruction may be made more concise after checking that the affected agent
still receives the concrete conditions, choice criteria, causal understanding,
implementation route and observation needed for the same type of task. Review
the effect in the actual medium. Longer text is not automatically better:
duplicates, contradictions and dead references harm decision quality.

## Permanent evidence and regression checking

The release-specific [lineage ledger](evidence/v1.13.0/lineage.json) records
observed historical sizes, at-risk source sections, current installed
destinations and specific restored details. Its associated test checks that
the identified sections and multiple concrete fragments remain in the
distributed content, not merely that the topic appears somewhere.

That test is a **structural regression alarm**. It cannot establish the
semantic fidelity of an edited paragraph or an agent's actual design decisions.
For substantive revisions, update the ledger and perform source-level review.
Do not weaken the regression alarm simply to make a shortened file pass.
Preserve older tags and historic review evidence unchanged.

## Review output

For a material change, the review should state the historical scope, original
and revised responsibility, observed shortening or relocation, whether an
independent design behavior survives, the evidence used to decide, concrete
restorations and any limitations. A representative old/new explanation should
show where an agent would act differently, not just compare file lengths.

An installed skill should let the agent solve real tasks using its own text:
current user intent, compatible mature sources, normal authorized acquisition,
human-centered rendering judgment, semantic and temporal behavior, local
validation and verified application outcomes. Maintenance proof is separate
from user acceptance and cannot be inferred from release publication alone.
