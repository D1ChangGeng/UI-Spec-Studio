# 多尺度设计证据地图：从设计认识到实际行动

## 这次增强解决什么

产品熟悉度、设计知识和当前任务中的实际观察需要分别确认。设计地图把重要对象、证据、判断、采用与验证连接起来；行动规则让重要缺口影响下一步。目标是让研究改变实际实现，而不是让记录看起来完整。

**强制的是重要决策的依据关系，按需选择的是记录形式和展开深度。** 已有项目记录、Markdown、任务说明都可以承担这项职责。可选 JSON 与检查器适用于需要自动检查的项目，不会自动创建额外工作流。

## 从整体到细节的六种尺度

| 尺度 | 研究与判断对象 | 可以回答的问题 |
|---|---|---|
| L0 产品体验目标 | 当前用户、主要任务、成熟参照、艺术目标和差异化 | 要对齐什么，为什么，哪些表达属于自己？ |
| L1 用户旅程 | 发起、持续、结果、返回、恢复和重新进入任务 | 用户怎样通过连续操作完成工作？ |
| L2 页面与界面结构 | 导航、工作区、辅助区域、弹层、响应式和共享框架 | 页面怎样在空间与任务上相连？ |
| L3 功能区域与组件 | 输入、内容、附件、工具栏、设置等及其状态 | 组成怎样工作，哪些成熟实现值得采用？ |
| L4 视觉关系与细节 | 字体、材质、图标、比例、留白、素材与动态节奏 | 成熟品质具体由哪些关系形成？ |
| L5 实现与验证 | 原始演示、试装、源码、资产、实际使用和检查条件 | 实际采用了什么，保留了什么，验证到哪里？ |

L5 同时关联前五层；六级不是六个必须按序通过的阶段。共享组件、字体和素材使用同一个对象标识，通过关系连接多个页面。状态与时间、使用条件、共享依赖、证据来源是横向关系，避免静态页面树遗漏真实体验。

## 发现最初没有想到的范围

先从用户任务推导范围，再用成熟产品的实际导航、教程、操作过程和材料挑战初始模型。对新发现分别判断“纳入、排除、待确认”，说明与当前产品任务的关系。反过来，当前产品独有而参照未覆盖的任务需要另寻成熟范式。

例如，对话应用的最初模型只有输入和消息。研究中发现附件处理失败、引用返回、历史继续或移动端键盘挤压，就需要判断是否改变范围。参照中的团队管理也可能有明确理由不纳入个人产品。覆盖率只针对已识别范围，不能用 100% 填写率证明没有未知遗漏。

## 一项重要设计决策需要哪些关系

**目的 → 研究问题 → 实际证据 → 专业判断 → 候选与选择 → 实现适配 → 验证与下一步。**

研究早期允许候选和实现为空，但要说明缺口及其下一步。已有验证的低风险局部调整可以继承已确认系统规则，并记录本次适用性检查。具有高品牌影响的小图标可能需要深入研究，其尺寸不决定研究成本。

这些关系直接进入已有[设计决策记录](../skills/ui-spec/assets/templates/design-decisions.md)，无需另写七份文档。重要决定需要可检查；并非每个 CSS 属性都成为决策单元。

## 状态是独立事实，而非完成阶梯

“待研究、已获取、已观察、已比较、已试装、已采用、已验证、受阻、经确认例外”各有证据对象与条件。一份已观察的候选可以被拒绝；已采用的组件可以在新主题下验证失败。视频已下载不能等同于已播放；组件已列入依赖不能等同于已使用；用户批准也不等于技术验证通过。

每条重要结论保留当前对象、版本与条件。源码、字体、主题或内容改变后，历史证据仍然存在，但对受影响条件的适用性应重新判断。授权例外保留范围、理由和来源，不改写成已验证。

## 从缺口选择行动

| 当前情况 | 下一步 | 可以承诺的范围 |
|---|---|---|
| 产品模型遗漏重要使用关系 | 研究任务与成熟产品、修订范围 | 已有依据的独立部分 |
| 只有功能文档，没有实际视觉 | 查看真实界面、交互演示、录屏或获授权材料 | 功能理解；视觉关系仍待确认 |
| 目标明确，候选在本项目适配未知 | 用真实字体、内容、主题和状态局部试装 | 范围明确、可回改的试装 |
| 候选过于相似，选择可能早期锚定 | 寻找有实质差异的方向并比较 | 暂定偏好，不扩大为已定方案 |
| 重要品质与适配已有依据 | 实施相关范围并检查整合结果 | 证据实际支持的对象和条件 |
| 整合后出现跳动、冲突或品质下降 | 定位理解、资源、适配、组合或运行层并复验 | 保留未受影响的决定，重开相关决定 |
| 低影响调整已有充分依据 | 继承规则、检查改动并收敛 | 避免无收益的额外探索 |

高影响缺口限制的是依赖它的重大承诺，并不冻结整个产品。独立工作可以继续，有限原型可以用来回答问题。记录一个后续行动不等于已完成该行动；下一轮应看到真实补证、试装、修订，或明确尚未解决的条件。

## 同一份记录的三种视图

**Overview** 展示目标、范围、新发现和主要缺口。**Design Detail** 深入指定页面、组件或资产的参照、比较、视觉解释和时序片段。**Execution & Assurance** 展示实际采用、源码、验证条件、未解决问题和下一步。

三个视图引用相同对象和证据，不各自维护一套互相漂移的状态。用户先看到结果与关键判断，再按需要展开细节。图、截图、运行入口与连续交互仍然是视觉审阅的主要依据。

## 可选的自动检查

[记录格式](../skills/ui-spec/references/evidence-records.md)提供可选 JSON 表达；[检查器](../skills/ui-spec/scripts/check_design_evidence.py)仅检查声明、引用和本地文件，不联网、不执行工具、不批准设计。

```bash
python <skill-dir>/scripts/check_design_evidence.py --project-root <project> --view overview
python <skill-dir>/scripts/check_design_evidence.py --project-root <project> --view detail
python <skill-dir>/scripts/check_design_evidence.py --project-root <project> --view execution --changed type-body
```

它只呈现字段、ID、引用、本地文件元数据、已声明关系和理论上尚无显式标记的类别。不再根据候选数量、证据种类、全局版本或缺口/动作组合裁定工作。`record_readability` 与结构问题分开；退出码 0 表示读取检查已运行，即使存在结构问题也不代表任务可以完成。专业证据适用性、研究真实性与实际 UI 品质仍由 Agent 和独立验证判断。详见[职责边界与升级说明](STRUCTURAL-INSPECTION.md)。

## 实际效果怎样判断

分别检查内容完整性、Agent 真实执行与最终 UI 品质。本轮提供[三组可比实验方案](experiments/design-evidence/PROTOCOL.md)及六类任务；准备工具只冻结输入和身份，不生成虚构实验结论。

基准版已经包含证据研究原则，所以要比较的是结构连接和行动约束的增量效果。真实试验需相同任务、模型、可用工具、访问条件及明确资源限制，保留工具轨迹和成品，由未看过分组的评审检查结果。低风险任务还要检验是否及时收敛。

完整执行规则在已安装的[地图方法](../skills/ui-spec/references/evidence-map.md)和[行动方法](../skills/ui-spec/references/evidence-actions.md)，这一说明只承担用户阅读入口。

## 当前模型、重要修订与原始证据

当前模型优先保存有效体验目标、实际采用、当前条件和未解决问题；重要修订解释什么认识变化、为什么变化、影响什么、现在采用什么判断；原始证据保留截图、媒体、资料、源码和运行记录。新证据可以重开任何相关决定，历史观察不因全局版本变化自动失效。两条主线——体验研究与判断、资源实现与验证——都保持双向修订。

理论类别未出现只能作为候选提示，不能自动成为项目缺陷。已声明目标缺少匹配记录与理论维度未标记分别报告。Agent 决定纳入、排除、合并、拆分或继续研究；检查器不生成执行指令，也不自动修改状态。
