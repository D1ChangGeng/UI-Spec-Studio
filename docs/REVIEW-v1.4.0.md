# 1.4 review: product intent and reference-grounded decisions

Baseline: v1.3.0, commit `36c0e9e48e358f5a7d932634ac9b6a6f49b52796`.
The source archive's Git tree was verified against the remote baseline before
editing. This release uses actual user feedback, file review, primary-source
research and a bounded authored browser scenario.

## Feedback evidence and interpretation

The user reported an unsatisfactory one-shot research-product SPEC: weak product
identity, opaque reference/resource choices and excessive influence from existing
presentation. The supplied image shows a research composer, navigation/history
and a recent-work region. It cannot establish which references the generating
agent read, whether the whole product is reachable, or runtime quality. Those
remain distinct from the reported experience and from our source-level diagnosis.

Review of 1.3 found useful but insufficiently explicit decision mechanisms:
product analysis used task/surface categories without a concrete user-level
interaction-model inference; existing implementation was an early reuse anchor;
high-impact confirmation was described broadly; resource records were optional
adoption details and could appear after decisions were settled. These are plausible
instruction-level contributors, not a claim about the hidden cause of one model run.

## Accepted design

Recognize the primary model through first action, working object, repeated loop,
continuation and result. Study comparable product conventions and engineering
resources while direction remains open. Preserve business/engineering contracts
and assess visual candidates against the target. Let users confirm material
alternatives with a concise recommendation; carry clear intent and delegation
forward. Connect the selected resources to actual surface states and results.

Shape remains an optional entry. The responsibility to resolve a material product
choice applies wherever the work begins. Six common references remain required;
no new runtime context manager or model-capability guarantee is introduced.

## Logical scenarios reviewed

| Condition | Expected decision |
|---|---|
| New ambiguous product | Infer candidates from use, study references, present a consequential choice before expanding a shell |
| Explicit conversational brief | Design its loop directly, with evidence and ordinary implementation initiative |
| Mature accepted design | Preserve the accepted direction and investigate changed needs only |
| Existing functional but unreviewed UI | Reuse business assets; assess presentation alongside alternatives |
| Explicit one-shot delegation | Produce a provisional recommendation, state assumptions and retain pending acceptance |
| Local correction | Apply the established model and affected principles at the appropriate scope |
| Unknown component source | Inspect exact demo/source/variant and record its visible target |
| Finish finds a conflicting contract | Reconcile real behavior, return the affected material decision, continue independent work |
| Missing browser or live reference access | Record the missing observation and keep claims at their actual evidence scope |

These are reasoning checks. Unit tests verify structure/mechanics; the authored
browser scenario executes its own UI. Independent agent evaluation and actual
Alpha project repair are outside this release's demonstrated scope.

## Scenario verification

The example compares conversation-first and object-first research with the same
content and theme roles. It uses real pinned Radix color values with MIT notice;
shadcn conventions are identified as structural technique transfer. Native dialog
and authored logic retain clear ownership. Sources are linked from the visible
record to actual files and controls.

The browser runner records four viewports, both models, both themes, targeted
contrast pairs, decision/source dialogs, focus, input, stop/retry, stale results,
long content, reduced motion and local persistence. The local in-memory renderer
retains storage verification as pending. CI uses HTTP and verifies actual browser
storage. Read generated reports and images for observed results; this file defines
the scope rather than pre-claiming execution.

## Mature-foundation refinement

The final revision makes design theory and resource knowledge work together in
search, browsing, comparison, selection, adaptation and verification. New surfaces
seek the highest appropriate reuse level, carrying coherent page/system/block
relationships before selecting isolated details. Resource discoveries can refine
the initial concept. This changes the default decision process rather than
introducing a resource quota.

The research example now uses an identified assistant-ui page composition as its
conversational foundation, with explicit preserved relationships and scoped
adaptations. Its native fixture is a design port, not a claim of integrating the
upstream React runtime. The source revision, license, adoption boundary and actual
browser observations are retained. Product acceptance stays with the user.
