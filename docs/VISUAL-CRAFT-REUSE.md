# 复用视觉工艺：从成熟成果到真实品质

## 本轮增强的核心

**优先复用已经成熟的视觉设计成果，而不只是实现功能的基础代码。**

专业知识首先帮助 Agent 理解体验、形成研究问题、发现优秀实现、解释品质来源、比较候选和完成适配。定制仍然有价值，但不应成为发现一个效果后立即重写它的默认动作。当前任务已有充分依据时，也无需为了证明研究而重复搜索。

## 选型的两个独立维度

| 维度 | 看什么 | 不能据此推导什么 |
|---|---|---|
| Reuse Scope（复用范围） | 页面、功能区块、组件体系、视觉组件、资产/效果、交互基础分别能承担什么职责 | 覆盖范围大不代表已经解决视觉问题 |
| Visual Completeness（视觉完成度） | 实际观察到的构图、排版、材质、状态与动态关系有多完整 | 名称、分类、依赖数和目录说明不能认证品质 |

适当范围内，优先选择已经解决更多有价值设计关系、且能够合理集成的实现。不是一律选择最大的模板，也不是一律选择最炫的组件。

**功能基础、视觉实现、整合后的感知品质**需要分别检查。可访问的交互原语、图标和 Markdown 渲染器可以提供重要功能，却不自动提供成熟输入区的比例、附件关系、材质与连续反馈。反过来，一个漂亮的视觉组件也可能仍需语义控件、业务状态和焦点机制。

## 专业知识怎样影响实际行为

把“高级”“自然”“有质感”转成可观察关系，再寻找相应成熟实现。例如，卡片的物体感可能来自翻面连续、枢轴、光照与稳定的背面，也可能来自静止文字旁的移动光影。二者对应不同资源和验证问题，而不只是同一个 rotateY 参数。

采用五个互相关联的分析视角：**感知目标 → 可观察关系 → 设计机制 → 成熟参照与实现 → 实际使用验证**。它们是判断方法，不是五份新表格。

字体研究关注实际字形、角色、字重、字距、行高、混合语言和光学关系；材质研究关注前后景、边界、光影、透明度与层次；构图研究关注视觉重量、阅读顺序、负空间及移动范围。专业知识的结果应体现为更好的搜索、选型或适配，不只是更精细地重写 CSS。

## 吸收 Finesse 的什么，不吸收什么

本轮阅读了固定来源版本的字体/材质方法、动效路线、交互运动及面向用户的表达说明。吸收其具体问题、因果解释、失败机制和可观察表达方式。

没有继承统一字体或数值、必须使用纹理/暗角/染色中性色、按产品类别降低表现强度、某些形式一律廉价、固定动效引擎顺序或完整示例代码。底色、渐变、玻璃、字体和布局形式都需要结合目标判断。专业工作界面可以具有鲜明的摄影、3D、排版和动态语言；真实工作中是否清晰、稳定、协调需要实际检查。

Finesse Skill 是本轮的方法研究来源。既有目录里的 Finesse UI 指向另一项 Figma 设计资源，两者不是同一个产品。

## 动效的三个问题

**效果**说明用户看到什么，**控制归属**说明时间线、滚动、用户输入和业务状态分别控制什么，**实现路线**说明哪个成熟组件或技术承接它。

拖拽弹层优先研究成熟实现对跟手、边界、释放速度、方向、吸附、取消和重新进入的处理；确有缺口再采用必要的采样、阻尼或 FLIP 技法。窗口、阈值和弹簧参数来自实际对象与设备条件，不直接复制来源配方。自动展示与直接操控的失败方式不同，不能互相替代证据。

减少动态需要保留可读、可操作且有设计意图的静态或简化状态。截图、稀疏帧与录屏分别保留其观察范围，不能据此声称真实设备的帧率或响应性能。

## 目录是入口，不是供应商边界

目录保留 37 个条目，增加 15 个描述性的职责/范围/视觉形式画像。React Bits、Vue Bits、Magic UI、Aceternity UI、Inspira UI 等提供视觉组件发现入口；完整页面、区块、功能基础与效果引擎仍有各自作用。

这些画像不提供质量评级，旧条目的研究日期没有被统一改新。实际选择仍需查当前原始 Demo、源码、版本、依赖和使用条件。已知库没有合适候选时，应扩展到其他作者、产品类别、作品、模板和实现生态，而不是自动退回自建。

```bash
python <skill-dir>/scripts/find_resources.py --form visual-component --stack vue --json
python <skill-dir>/scripts/find_resources.py --form blocks --stack react --json
```

结果仍按名称排序；工具只返回匹配资料，不决定下一步动作。

## 从参照到实际采用

保持 **体验目标 → 真实参照 → 候选 → 原始演示 → 项目试装 → 实际集成 → 整体使用验证** 的关联。通过配置、变量与组合保留成熟机制，只有具体需求才修改内部结构。主题、字体、内容、容器或状态变化后，检查原有品质是否仍成立。

记录选用了什么、它解决了什么、保留和改动了什么，以及在哪里看到实际结果。项目内的依赖声明不是采用证明；采用证明也不是整合品质证明。损失可能来自资源本身、适配、内容或组合关系，修复应返回相应层级。

外部成熟作品承担主要正向实例职责。Skill 保存方法和小型因果示例，不收录大型演示库、字体或大量第三方组件源码。

## 检查器边界保持不变

六级地图、当前模型/重要修订/证据档案继续使用。结构检查器仍只描述字段、对象和声明关系，不给资源打视觉分、不要求候选数量、不判断是否必须继续搜索。所有安装脚本和结构检查器在本轮保持字节不变。

## 实证边界

[版本评审](REVIEW-v1.16.0.md)区分源码改进、结构测试、维护者实际试装、README 自应用与独立 Agent 实验。实际运行一个候选并观察结果，可以支持该对象的适配判断；不能用它证明整个版本对所有任务、模型或用户都提升品质。
