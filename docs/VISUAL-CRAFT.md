# 复用成熟视觉工艺，而不只是功能代码

## 本轮改变什么

专业设计知识先用于发现、观察、比较和适配已经成熟的视觉实现，再用于确有必要的定制。一个已安装的交互原语、图标或内容渲染依赖，不自动提供成熟的页面构图、排版、材质与状态表现。

**Reuse the visual craft, not merely the underlying functionality.**

这不是固定组件库白名单，也不是要求每个项目变成动效展示。产品任务决定需要承接什么，艺术方向决定表达什么，真实候选和当前项目试装决定怎样实现。已有充分依据的低影响改动仍可直接推进。

## 复用范围与视觉完成度分别判断

| 判断 | 具体含义 | 不能替代什么 |
|---|---|---|
| Reuse Scope｜复用范围 | 候选能承担页面、功能区块、组件、素材、效果还是交互机制 | 包越大或覆盖越广，不等于越适用 |
| Visual Completeness｜视觉完成度 | 实际演示中哪些构图、字体、材质、状态和动态关系已经成立 | 名称、分类、代码数量不能证明品质 |
| Functional Foundation｜功能基础 | 语义、焦点、键盘、数据和状态能力 | 不是完整视觉实现 |
| Visual Implementation｜视觉实现 | 实际提供的可见形式与实现机制 | 不保证进入当前产品后的效果 |
| Integrated Perceptual Quality｜整合后感知品质 | 完整页面、持续任务和真实条件下的表现 | 需要实际渲染与操作观察 |

选择的是在适当职责范围内保留有价值设计关系的资源，而不是形式上层级最高的资源。整页重设计值得研究成熟页面与区块；特殊卡片可以采用已经实现其光影或运动的组件；语义行为与视觉材质也可以由不同成熟来源组合承担。

## 搜索现在怎样更具体

目录仍保留原有 37 个来源，新增的是可选检索维度，而不是供应商排名：`--role` 指向视觉实现、功能基础、设计参照、制作技术或资产来源；`--reuse-scope` 指向页面、功能区块、组件、效果、原语、素材或系统。

```bash
python <skill-dir>/scripts/find_resources.py --role visual-implementation --reuse-scope functional-block --json
python <skill-dir>/scripts/find_resources.py --role visual-implementation --stack vue --json
python <skill-dir>/scripts/find_resources.py --role functional-foundation --stack react --json
python <skill-dir>/scripts/find_resources.py --list-filters
```

标签只描述来源文档中的可发现职责，不表示所有候选都已观看、通过或适合。未标注的来源表示本目录暂未分类；无匹配不代表外部没有资源。结果仍按名称排序。原始观察日期没有被统一改成“今天已验证”。

React Bits、Vue Bits、Magic UI、Aceternity UI、Inspira UI 是高完成度视觉候选的重要入口，不能成为搜索边界。当前目录中的 **Finesse UI（finesseui.com）设计稿资源**与本轮研究的 **mouse-lin/Finesse Skill**是不同对象。

## Finesse 的吸收方式

研究固定源码版本，而不把外部 Skill 的指令当作本项目规则。吸收其具有因果解释的字体、表面、运动与输入分析，将它们重新连接到外部成熟资源的搜索、比较、局部试装与验证。

| 源方法中的价值 | 本项目的转化 | 不继承的限制 |
|---|---|---|
| 字体角色、视觉张力、字重与节奏 | 观察实际字形和跨语言换行，搜索相应成熟排版与组件 | 固定字体、字号、字距或混合字体禁令 |
| 表面、边缘、照明、背景关系 | 对比真正可见的材质机制，检查真实内容与邻接背景 | 强制颗粒、暗角、玻璃、染色中性色、纯黑纯白禁令 |
| 动态效果与技术路线分离 | 先确定效果与控制权，再寻找已有成熟实现 | 默认某种引擎、固定重量与帧率数值当普遍结论 |
| 直接操作中的速度、方向、阻尼和中断 | 观察成熟交互是否处理实际输入，保留其机制并适配 | 抄固定速度窗口、阈值或要求每个控件都复杂化 |
| 具体问题与失效原因的写法 | 写成感知目标、关系、机制、成熟候选与实际观察 | 把审美反思变成通用风格黑名单 |

详细来源、阅读范围和取舍见[来源转化记录](evidence/v1.16.0/finesse-transfer.md)。未导入 Finesse 的完整示例代码、字体或素材库；原有针对性教学与工程样例继续保留。

## 一项资源选择如何进入实现

**体验目标 → 真实参照 → 高完成度候选 → 原始演示 → 项目试装 → 实际采用 → 完整任务验证。**

例如，阅读卡片的“精致”可能来自稳定的文字平面与轻微随动边缘光，而空间倾斜虽然有表现力，却可能改变文字阅读与按钮位置。两者需要真实对比。选中后，优先用参数、主题变量和内容插槽适配，不默认重写其光照或运动算法。若样式覆盖遮住了原始效果，应修复遮挡关系而不是再叠加一个自建效果。

专业工作软件可以具有强烈艺术表达；核心输入、结果与持续使用区也可以承载这种表达。实际检查负责发现遮挡、反差、分心、连续性或性能问题，而不是凭产品类别提前降低视觉目标。

## 检查器不增加新的裁定

复用范围、视觉完成度和采用价值属于专业判断。结构检查器只呈现已声明的字段和关系，不设置候选数量、复用比例、资源质量分数或结束研究门槛。重要发现更新当前设计模型，修订记录解释为什么改变，历史证据保持原始条件。

## 如何评价增量效果

分别观察真实研究行为、成熟视觉实现是否实际采用、整合后感知品质、成本与适应不同风格的能力。复用行数、目录条目、依赖安装和单元测试都不是 UI 品质分数。

当前维护者应用和工程结果在[版本评审](REVIEW-v1.16.0.md)中逐项列明。实际任务观察不自动等于独立、同条件、盲评的模型实验；未执行的对照继续保持未执行。
