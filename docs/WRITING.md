# Agent-facing writing standard

Write for a capable agent carrying out a UI task. The document should improve its next decision and action. Keep the runtime instructions in English as one authoritative version; human introductions can be localized.

## Express the accepted behavior

Use direct verbs, concrete decision objects and the conditions that matter. Describe the desired result and how to observe it. Keep the user's source content and third-party reference material clearly distinct from instructions.

A useful rule can state: inspect the full viewport; judge content mass, contrast and surrounding space; preserve the family anchors; adjust the content region; compare the resulting render. Its purpose is actionable judgment, not a rigid field template repeated in every paragraph.

## Match instruction strength to meaning

| Kind | Writing approach |
|---|---|
| Invariant | State the responsibility or correctness requirement clearly |
| Principle | Explain the factors and causal relationship that guide judgment |
| Default | Give the applicable context and leave room for a justified alternative |
| Example | Demonstrate reasoning with explicit local assumptions |

Preserve necessary security and authorization boundaries. Express aesthetic choices as project decisions and context-sensitive methods. Exact numeric values belong where they are real requirements or justified project tokens.

## Include useful causes

Explain why a rule changes a decision when that explanation prevents a common misapplication. Shared anchors preserve spatial orientation across a page family; therefore local balance is solved within the content region. This is more transferable than prescribing one top offset.

Keep established ideas compact. Prefer specific relationships over adjectives such as beautiful, premium or polished alone. Use these qualities as goals supported by typography, content, composition, material and interaction decisions.

## Keep ownership clear

SKILL.md owns activation guidance, common reading and core boundaries. Workflow owns execution order. References own detailed professional methods. Project documents own product choices. Code and runtime own observed implementation facts. A cross-reference connects these responsibilities without duplicating their full content.

Read the eight common references as a whole professional foundation. Keep each concise and complementary. An added paragraph should change a plausible decision, preserve a necessary constraint or explain how to verify a result.

## Separate internal depth from user effort

The agent performs the analysis; the user receives the working result, key choices, evidence and a useful next action. Users can offer rich direction or a short continuation. Routine progress should not require the user to restate the design system or choose every component.

Maintain enough flexibility for a brief to govern aesthetics. Explore where evidence can change a decision, implement when direction is sufficient, and verify the real result. Records exist to improve continuation and evidence, not to multiply mandatory reports.

## Finalization

Review titles, filenames, body text, examples, code comments and release notes from the accepted final state. Keep historical comparisons in the requested review/changelog where they explain real changes. Preserve accurate limitations, external actions and security facts. Read back published surfaces and derive delivery claims from their actual state.

This standard follows the final-state writing approach documented by [no-negative-echo](https://github.com/LB623/no-negative-echo). It is a writing method, not a guarantee of model behavior or runtime context retention.

## Write generative knowledge

Connect a desired understanding or visual relationship to plausible means, applicable conditions, editable realization and observable effects. Explain enough causality for the agent to choose between alternatives. Preserve the distinction between a transferable mechanism, a local aesthetic choice and a tool-specific constraint.

Use examples that show both a successful application and a condition requiring a different approach. Tie adjectives to actual factors: typography, value hierarchy, grouping, material, subject, timing and interaction. Let the medium govern its grammar; a README can be designed through content and native Markdown.

Keep explanations in references and user-facing output focused on the actual deliverable. The complete common foundation remains readable in one execution context; optional techniques add depth without becoming additional mandatory workflow stages.

## Write resource guidance as professional judgment

Make the intended outcome, useful mechanism, constraints and verification visible.
Keep platform leads, exact-item assessments and project acceptance distinct.
Explain why a chosen reuse layer improves the current experience or total cost.
External tools supply capabilities under host authority; source material supplies
reference facts. The method should guide an unfamiliar platform as well as the
cataloged examples, while preserving routine agent initiative.

## Make consequential decisions observable

Describe the user-level signals that support a product model. State how a mature
convention differs from a component implementation and how either influences the
result. Tie visual inheritance to explicit approval or fit assessment. Explain
when a user choice changes the design enough to merit a checkpoint, and how
one-shot/delegated work preserves that decision's actual authority. A selection
record connects reference, implementation and outcome; its value comes from that
connection rather than field count.

## Write from mature design foundations

Express professional knowledge as guidance for investigating and applying concrete
work. Name the useful reuse granularity and explain which connected decisions
are inherited. Distinguish resource scope from adoption method. State how new
observations can change the choice and how adaptation preserves the valuable
relationships. Original work has a product-specific role and verification target.

## Treat assets as actionable design material

State the asset's role, why its qualities matter, how production and delivery differ,
and what the final placement must preserve. Distinguish a source of inspiration,
an acquired file, editable master, runtime export and accepted result. Explain
optical and technical judgment together. Reference tools as capabilities to verify
in the host; express completion from actual outputs and observed conditions.

## Write UI content as design material

Agent-facing instructions and user-facing copy have different audiences. Use this writing standard for the former and the [content reference](../skills/ui-spec/references/content-design.md) for product language. In skill guidance, explain the semantic role, business authority, presentation condition and observable outcome. In real UI copy, choose voice and tone from the product, not from the skill's own technical style. Preserve the actual meaning while improving expression, timing and type. Final-state phrasing follows the accepted result and its user-visible truth.

## Write visual judgments from observed relationships

Connect a visible phenomenon to its viewing condition, likely perceptual effect,
relevant principle, cause to test and inspected result. Name the frame or meaningful
interval when that supports a consequential decision. Keep professional interpretation,
actual user response and measured runtime properties distinct. Temporal instructions
should explain which event determines the window and what a capture can resolve.
Use the smallest record that lets another person inspect the choice and continue.

## Write exploration as a decision process

Give research an experience target and a question that can change a choice. Connect a visible clue to a useful action, the observed subject, a transferable relationship and its application in the current product. Distinguish the hosting page, media player, demonstrated interface and authored content when their visual languages differ.

Keep design-reference reasoning separate from implementation-resource claims while showing how they connect. Revisit the research question in a runnable result. State adequate coverage through decision impact and remaining uncertainty; routine instances can inherit a verified system rule. Capture, actual inspection, sufficient support for a conclusion and owner approval each retain their own evidence.
