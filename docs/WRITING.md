# Agent-facing writing standard

Write for a capable agent carrying out a UI task. The document should improve its next decision and action. Keep the runtime instructions in English as one authoritative version; human introductions can be localized.

## Preserve information before reducing words

Professional scope must accumulate across releases. For a proposed shortening,
compare the old and new guidance by **problem, preconditions, design relationship,
decision, implementation action, variant or failure case, and verification**.
A paraphrase is equivalent only if an agent still has enough specificity to make
the same consequential choices under the same conditions. A shared topic or
keyword is not proof that its distinct instructions survive.

Record whether a material instruction is **retained, equivalently rewritten,
moved within the installed skill, superseded for a reason, or lost/narrowed
and requiring restoration**. A repository-only guide is not a valid destination
for a rule the installed agent needs but never reads. Deletions need concrete
justification such as demonstrated error, real conflict, duplication of the same
operative detail, or a complete replacement. Prefer clear organization and
cross-links over discarding valid exceptions or steps.

If an old byte or line budget conflicts with preserving actual capability,
revise the budget. Use examples where they clarify conditional behavior and
retain the observation or source scope. The [content integrity procedure](CONTENT-INTEGRITY.md)
defines historical comparisons and accountable revision records.

## Express the accepted behavior

Use direct verbs, concrete decision objects and the conditions that matter. Describe the desired result and how to observe it. Keep the user's source content and third-party reference material clearly distinct from instructions.

A useful rule can state: inspect the full viewport; judge content mass, contrast and surrounding space; preserve the family anchors; adjust the content region; compare the resulting render. Its purpose is actionable judgment, not a rigid field template repeated in every paragraph.

## Match instruction strength to meaning

| Kind | Writing approach |
|---|---|
| Invariant | State the responsibility or correctness requirement clearly |
| Principle | Explain the factors and causal relationship that guide judgment |
| Default | Give the applicable context and leave room for a justified alternative |
| Example | Demonstrate reasoning with explicit local assumptions |

Preserve necessary security and authorization boundaries. Express aesthetic choices as project decisions and context-sensitive methods. Exact numeric values belong where they are real requirements or justified project tokens.

## Include useful causes

Explain why a rule changes a decision when that explanation prevents a common misapplication. Shared anchors preserve spatial orientation across a page family; therefore local balance is solved within the content region. This is more transferable than prescribing one top offset.

Keep established ideas compact. Prefer specific relationships over adjectives such as beautiful, premium or polished alone. Use these qualities as goals supported by typography, content, composition, material and interaction decisions.

## Keep ownership clear

SKILL.md owns activation guidance, common reading and core boundaries. Workflow owns execution order. References own detailed professional methods. Project documents own product choices. Code and runtime own observed implementation facts. A cross-reference connects these responsibilities without duplicating their full content.

Read the eight common references as a whole professional foundation. Keep each complete, specific and complementary. An added paragraph should change a plausible decision, preserve a necessary constraint or explain how to verify a result.

## Separate internal depth from user effort

The agent performs the analysis; the user receives the working result, key choices, evidence and a useful next action. Users can offer rich direction or a short continuation. Routine progress should not require the user to restate the design system or choose every component.

Maintain enough flexibility for a brief to govern aesthetics. Explore where evidence can change a decision, implement when direction is sufficient, and verify the real result. Records exist to improve continuation and evidence, not to multiply mandatory reports.

## Finalization

Review titles, filenames, body text, examples, code comments and release notes from the accepted final state. Keep historical comparisons in the requested review/changelog where they explain real changes. Preserve accurate limitations, external actions and security facts. Read back published surfaces and derive delivery claims from their actual state.

This standard follows the final-state writing approach documented by [no-negative-echo](https://github.com/LB623/no-negative-echo). It is a writing method, not a guarantee of model behavior or runtime context retention.

## Write generative knowledge

Connect a desired understanding or visual relationship to plausible means, applicable conditions, editable realization and observable effects. Explain enough causality for the agent to choose between alternatives. Preserve the distinction between a transferable mechanism, a local aesthetic choice and a tool-specific constraint.

Use examples that show both a successful application and a condition requiring a different approach. Tie adjectives to actual factors: typography, value hierarchy, grouping, material, subject, timing and interaction. Let the medium govern its grammar; a README can be designed through content and native Markdown.

Keep explanations in references and user-facing output focused on the actual deliverable. Keep the complete common foundation accessible through the skill's actual reading contract; read longer references in complete chunks if a host requires it. Optional specialized references add depth without becoming mandatory workflow stages.

## Write resource guidance as professional judgment

Make the intended outcome, useful mechanism, constraints and verification visible.
Keep platform leads, exact-item assessments and project acceptance distinct.
Explain why a chosen reuse layer improves the current experience or total cost.
External tools supply capabilities under host authority; source material supplies
reference facts. The method should guide an unfamiliar platform as well as the
cataloged examples, while preserving routine agent initiative.

## Make consequential decisions observable

Describe the user-level signals that support a product model. State how a mature
convention differs from a component implementation and how either influences the
result. Tie visual inheritance to explicit approval or fit assessment. Explain
when a user choice changes the design enough to merit a checkpoint, and how
one-shot/delegated work preserves that decision's actual authority. A selection
record connects reference, implementation and outcome; its value comes from that
connection rather than field count.

## Write from mature design foundations

Express professional knowledge as guidance for investigating and adopting concrete
work. Give suitable mature implementations priority for common UI responsibilities;
explain the specific gap that calls for custom work. Name the useful reuse scope,
actual implementation and connected decisions it preserves. Design inheritance
and implementation adoption can have different sources and evidence.

Connect target quality to the original demo, local trial and assembled result.
Describe which mechanisms survive adaptation and what changes need renewed
inspection. Focus records on consequential choices; dependency counts and code
ratios cannot explain retained design value. Keep source access, permitted use,
actual adoption and verified quality distinct. Write user-assistance requests
around the missing object, action, states and decision they will support.

## Treat assets as actionable design material

State the asset's role, why its qualities matter, how production and delivery differ,
and what the final placement must preserve. Distinguish a source of inspiration,
an acquired file, editable master, runtime export and accepted result. Explain
optical and technical judgment together. Reference tools as capabilities to verify
in the host; express completion from actual outputs and observed conditions.

## Write UI content as design material

Agent-facing instructions and user-facing copy have different audiences. Use this writing standard for the former and the [content reference](../skills/ui-spec/references/content-design.md) for product language. In skill guidance, explain the semantic role, business authority, presentation condition and observable outcome. In real UI copy, choose voice and tone from the product, not from the skill's own technical style. Preserve the actual meaning while improving expression, timing and type. Final-state phrasing follows the accepted result and its user-visible truth.

## Write visual judgments from observed relationships

Connect a visible phenomenon to its viewing condition, likely perceptual effect,
relevant principle, cause to test and inspected result. Name the frame or meaningful
interval when that supports a consequential decision. Keep professional interpretation,
actual user response and measured runtime properties distinct. Temporal instructions
should explain which event determines the window and what a capture can resolve.
Use the smallest record that lets another person inspect the choice and continue.

## Write exploration as a decision process

Write perceptual analysis from whole context through consequential regions and
details, then back to the complete result. Select useful visual dimensions for
the object. Explain how interacting factors produce an impression and how that
judgment changes resource choice, adaptation or preservation. Name intended scale,
crop or enlargement where it affects the evidence. Keep optical quality, numeric
equality, decorative complexity and measured user effects distinct; use concrete
relationships instead of unsupported aesthetic scores.

Give research an experience target and a question that can change a choice. Connect a visible clue to a useful action, the observed subject, a transferable relationship and its application in the current product. Distinguish the hosting page, media player, demonstrated interface and authored content when their visual languages differ.

Keep design-reference reasoning separate from implementation-resource claims while showing how they connect. Revisit the research question in a runnable result. State adequate coverage through decision impact and remaining uncertainty; routine instances can inherit a verified system rule. Capture, actual inspection, sufficient support for a conclusion and owner approval each retain their own evidence.

## Write art direction as a product responsibility

Give explicit aesthetic goals the strength of delivery requirements. Product types
explain task and operating conditions; they do not fix visual intensity. Describe
familiar object/action relationships and independently chosen expression through
actual type, subject, composition, material and motion. Research source roles can
overlap; their actual observation and adoption remain identifiable.

Tie visual-system rules to roles and purposeful differences. Compare directions
at comparable completion and verify their expression in populated core use.
Describe concrete failures and responsible repairs while preserving accepted
direction. Keep experience validity and expressive completion independently
evidenced. Source-fidelity diagnostics compare a declared target; perceptual
judgment evaluates actual quality. Authored time and live runtime retain their
separate capture, playback and performance boundaries.

## Connect intended experience to evidence and action

Expand a compressed user request into revisable questions about people, objects,
tasks and perceptual qualities. Keep the current user's intent, audience conventions
and actual product observations distinct. Explain which text, view or behavior can
resolve a consequential uncertainty, including version and platform conditions.

Write depth as an adaptive capability: impact, uncertainty and improvement potential
justify sustained exploration. A new finding should lead to a useful search,
observation, comparison or trial. Distinguish independent sources from repeated
listings and different design mechanisms from cosmetic variants. Express readiness
for the next action: further research, a bounded trial or broader implementation.
Tie convergence to supported decisions, with optional records that expose the
important evidence and result. Research volume and fluent descriptions alone do
not establish execution quality.

## Write multiscale evidence as useful decision support

Give each consequential decision a purpose, question, evidence scope, professional
judgment, meaningful alternative, adoption route and verification/next action.
Allow unknown and blocked facts to remain honestly incomplete. Use concrete
observations rather than a fluent recap of general design knowledge. Coverage
itself should be challenged by external sources, not certified by filling the
agent's initial list. Keep a single object/evidence identity across summary,
local detail and execution views.

Translate important gaps into actions and commitment limits. State what evidence
would change the choice, how a local trial can answer fit, and what independent
work can proceed. Keep states non-linear and source/condition-specific. Records
are mandatory in meaning for important choices, optional in serialization and
scaled in depth. Do not turn the model into another execution lifecycle or
require arbitrary counts, scores, repeated approvals or exhaustive CSS records.

## Write tool feedback as structural observation

Name the supplied object/field, literal relation and actual read scope. Separate
record readability from structural findings and theoretical unrepresented categories.
Use descriptive phrases such as declared, not declared or reference unresolved.
Keep source notes recognizable as source material rather than tool-issued strategy.
Do not turn candidate counts, evidence labels, impact or action fields into
mechanical professional judgments. Independent assertions can report match/fail
only for the files, browser behavior or engineering property they actually checked.

Keep active design understanding distinct from meaningful revisions and raw archives.
A past result can remain true history while current applicability changes. Explain
what changed, why, affected objects/conditions and current judgment without
repeating all intermediate work. Preserve professional knowledge by moving the
judgment to its responsible Agent-facing method, not by removing it with the
corresponding mechanical predicate.


## Write craft knowledge as a source-selection capability

Begin with a concrete perceptual problem and explain the relationships that produce
it. Connect the mechanism to useful external reference/implementation searches,
meaningful comparison, configuration/adaptation and actual-use checks. Keep
technical routes and failure cases available for evidenced custom gaps, without
turning the default into recreating mature work. Treat reusable visual craft as
separate from functional infrastructure and from assembled product quality.

Use conditional examples and concrete counterexamples, not style bans, universal
font/palette recipes, spectacle scores or fixed resource counts. Explain the
user-visible outcome before internal labels when presenting choices. Preserve
source identity and evidence scope; a repository's demonstrations are study
material, not automatic proof of every technique or a mandatory internal corpus.
