# Independent source and process audit

**Cohort:** replication-20261028-20e56  
**Scope:** all twelve assigned frozen outputs; nonblind source/process assessment, separate from the blind visual review.  
**Arms:** A is full production UI Spec v1.15.0; B is full production v1.16.0.  
**Machine-readable record:** [process-audit.json](process-audit.json)

## Principal findings

All twelve runs integrate externally sourced material, but the scope of that material varies substantially. The clearest repeated source distinction is in T3: both B runs retain Vaul 1.1.2's concrete drawer movement, drag feedback and release/settling implementation, with targeted local patches. Both A runs use Radix and Motion as modal and animation foundations while authoring their gesture policies locally. This is evidence of different implementation choices. It does not establish better perceived motion, higher overall visual quality, reduced work, or a causal effect of the instruction revision.

T1 shows considerable commonality across arms: all four outputs adapt small source-card arrangements from the same pinned Vane source, with composer arrangement also attributed and supported in three runs. The surrounding Folio products remain substantially custom. T2 is mixed: A repetition 1 actually imports Tabler CSS and uses its component families; A repetition 2 and B repetition 1 translate different portions of shadcn Card/Table; B repetition 2 adopts a narrower Button/Badge family. This is a concrete counterexample to describing A as merely primitive-based or B as uniformly adopting larger visual systems. No run establishes adoption of an entire external product system. [T1 adaptation](frozen/n08f925c8/app/src/components/ResearchUI.jsx), [Tabler import and custom CSS](frozen/nb3bf2299/app/src/styles.css), [A2 shadcn adapters](frozen/n6c114121/app/src/components/ui.jsx), [B1 shadcn adapters](frozen/n957b09e9/app/src/ui.jsx), [B2 shadcn adapters](frozen/n91d1fa87/app/src/ui.jsx).

Both instruction versions already contain substantial mature-sourcing guidance, including useful reuse scope, original-demo/local-trial inspection and integrated verification. B strengthens the language about resolved visual implementations and appropriate scope. The evidence therefore supports a comparison between two substantial production instructions, not a sourced-versus-unsourced experiment. The actual decisions below are established from retained code and execution evidence rather than inferred from those instructions. [A sourcing reference](frozen/nb8be8a13/skill/references/component-sourcing.md), [B sourcing reference](frozen/n08f925c8/skill/references/component-sourcing.md), [A skill](frozen/nb8be8a13/skill/SKILL.md), [B skill](frozen/n08f925c8/skill/SKILL.md).

All four T3 outputs preserve the supplied domain, accepted notebook component and accepted notebook stylesheet exactly. Their navigation change is only Saved → Library, retaining the existing ID, icon and count. The source audit found one concrete missing notice for retained assistant-ui comparison material; the coordinator resolved it through a separately retained, byte-matched official notice/provenance record. Existing supplemental runtime notices cover the inspected actual runtime packages. Bare `dist/`, frozen `app/` and the complete evidence delivery have different notice coverage; that distinction remains material.

## Method and interpretation

This audit followed [SOURCE-AUDIT-TASK.md](SOURCE-AUDIT-TASK.md), [PROTOCOL.md](PROTOCOL.md), [process-audit-rubric.json](process-audit-rubric.json), [INSTRUMENT-NOTES.md](INSTRUMENT-NOTES.md) and [assignment.json](assignment.json). Each implementation was inspected only after its `FROZEN.json` became available. No live participant work, blind review records, anonymous maps or visual scores were inspected. Participants and reviewers were not contacted. No participant source, manifest or raw evidence was changed.

For each run, I read actual imports and call sites, source snapshots, relevant CSS/assets, acquisition records and consequential command output. I compared the two vendored Vaul modules to their retained original tarballs, followed surviving mechanisms into the integrated sheet, and separated local adaptations from upstream responsibilities. I independently checked every manifest-listed `app/src`, `app/public`, `skill` file and `app/package.json`; all matched their frozen hashes. Counts of checked files document coverage only. They are not quality measurements.

The classifications in the JSON deliberately separate `font_or_icon`, `behavior_foundation`, `static_visual_implementation`, `temporal_visual_implementation`, `composed_region` and `product_system`. A run can contain several. A foundation can be useful and visually consequential without supplying a resolved component composition. Likewise, a concrete drawer release implementation can carry visual craft even if its surface styling is rewritten. No additive maturity score is constructed.

A recorded screenshot proves capture, not that the participant viewed it. `viewed.md` and handover claims remain attestations because exported image-view tool traces are unavailable. I inspected two retained original-demo images for the final A T3 run solely to resolve whether they show open dialogs; I did not rate application aesthetics. A source read printed into a command log proves retention/read execution, not successful cognitive use. Original-demo operation, local trial, final verification and owner acceptance are separate facts throughout this report.
