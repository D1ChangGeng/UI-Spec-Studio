# Adaptive formal increments: registered application study

## Question and scope

Does explicit scope judgment, and then the complete formal-increment mechanism,
change how an Agent realizes important qualities in an evolving product?
The comparison concerns appropriate boundaries, depth, actual rendered quality,
integration and useful delivery. More SPECs, more records and passing code tests
are not measures of design quality.

This is a bounded, exploratory study: three conditions across three task families,
with a continuation in each family. Each condition/family starts a fresh Agent
thread with the same inherited model configuration and tools. There is one
independent run per cell (nine runs), not enough to estimate model variability
or establish general causal effectiveness. The same Agent performs a cell's
continuation so that accumulated-product behavior can actually be observed.

## Conditions fixed before execution

- **A — published method:** exact complete v1.16.1 runtime, also unchanged on
  main commit `9cc2470e21b626c56dd293274277d9809c13defb`.
- **B — scope judgment:** A plus the installed entry pointer and the single
  `judgment-module.md` instruction supplement. This introduces closure factors
  and keep/split/merge/redraw judgment without the full formal-increment records,
  init candidate structure or cross-SPEC continuity additions.
- **C — integrated method:** complete candidate v1.17 runtime. The frozen
  manifest identifies every byte. Record any subsequent release correction
  separately; do not describe an untested revision as the tested snapshot.

Core visual, content, resource and temporal knowledge is retained. C also changes
optional templates and the neutral inspector, so B/C is an integrated-method
comparison rather than an isolated single-sentence experiment. Participants use
neutral cell names and receive only their own Skill, task and starter files;
they do not receive this protocol, condition map, hypotheses, scores or another
participant's output. Source files can reveal version information; this is not
a claim of participant blinding.

## Tasks and continuation

| Family | First task | Follow-up on the same implementation | Coverage |
|---|---|---|---|
| T1 | Evolve a conventional notebook workspace with collection and editing | Shared bilingual typography and density refinement | Stable SaaS structure; shared visual system; avoid gratuitous splitting |
| T2 | Build the core of a conversational research workspace from available references | Add coordinated source reading during a long response | Complex conversation; cross-component state/time; continuous product evolution |
| T3 | Refine a card-based saved-note interaction | Extend it to a coherent collection and reversible return | Fine motion; preparation/interruption; multiple related increments |

Task texts are frozen alongside the common starter identities. Follow-ups are
withheld until the first result is recorded. They are new user work, not tailored
coaching in response to a condition's performance. Existing artifacts are copied
before continuation so before/after states and original failures remain available.
All sources are public repository examples with synthetic content and local
browser persistence; no live customer systems or real service commitments are used.

## Comparable execution conditions

Each cell gets the same task-specific starter, tooling note, available reference
corpus, model configuration and tools. Allow up to 18 minutes for the initial task
and 8 minutes for continuation. This is an experimental execution ceiling, not a
Skill research quota or evidence-sufficiency rule. Record actual elapsed time;
early completion does not earn additional time in another condition. Infrastructure
interruptions and restarts are recorded separately, never silently credited to
the method. Keep network/tool restrictions identical where possible and disclose
differences. No model override is requested. Record exact backend identity only
if the host supplies it; do not invent token counts or model version evidence.

The maintainer may fix the shared test environment before the first run. During
execution, assistance is limited to neutral infrastructure facts delivered to all
affected conditions. No arm receives design advice, expected outputs or targeted
repair prompts. A bounded session ending with an incomplete product is retained as
an incomplete result, with its working quality and missing goal coverage reported.

## Evidence and assessment

Retain input hashes, start/end facts, task messages, participant final delivery,
initial/final source, adopted-source records, command logs, captures and factual
runtime checks. A participant-authored activity record is not a complete host
transcript; distinguish it from captured test output and independently observed
results. Capturing an image is distinct from viewing it.

Review the five outcomes separately:

1. Scope suitability: unnecessary splits, diluted responsibilities, preserved
   dependencies, and traceability of deferred/open goals.
2. Method depth: actual reference inspection, source comparison/adoption, local
   realization and appropriate observed conditions at important objects.
3. Quality realization: composition, type, material, controls and full temporal
   relationships actually visible in the running product.
4. Product coherence: retained useful work, shared systems and complete affected
   tasks across continuation, including regressions and false product claims.
5. Execution and communication: repeated work, repair burden, observed time and
   the usefulness/accuracy of user-facing results.

Use condition-anonymous output packets for independent Agent review of final
screens and behavior. Explain specific visible facts and tradeoffs; do not turn
an aesthetic score into a statistical result. Engineering assertions have their
own explicit contracts. Record reviewer identity as an Agent, not a human user.
No actual owner acceptance or target-device smoothness is claimed without that
separate observation. Root synthesis can use the disclosed condition map only
after independent reviews are saved.

## Release interpretation

Publish all completed and incomplete cells and relevant failures. Report which
scope decisions improved, held steady or regressed in these particular tasks.
State unresolved confounds: one sample per cell, model stochasticity, time limits,
reference access, author/reviewer tools, fixture-to-production transfer and any
unobserved continuous behavior. Publish implementation and instruction improvements
on their supported evidence, while leaving broad perceptual-effectiveness claims
open when the study cannot establish them.
