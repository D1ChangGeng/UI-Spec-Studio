# Independent product-output review instructions

You are reviewing three implementations of the same two-stage product task.
Use only your assigned packet, its infrastructure paths and public documentation
needed to operate the supplied tooling. Do not inspect sibling packets, parent
project records, participant design accounts or experimental condition mappings.
Variant labels are anonymous. Do not try to infer which instruction set produced
an application. This is product review, not an implementation task.

Read TASK-initial.md and TASK-continuation.md. Each variant contains exact initial
and final application source. Preserve those files. Start local HTTP servers with
distinct origins and use fresh browser contexts to avoid shared storage keys.
Use TOOLING.md for the available test browser, Python and font configuration.
Save your scripts, original test failures, captures and findings in review-output/.

Operate the actual final applications and view their rendered pixels at 1440×900
and 390×844. Use comparable representative content and task conditions across all
three variants. Inspect the first implementation where it helps distinguish an
inherited relationship from the continuation's change. Allocate attention evenly
within an approximately 18-minute review session and state any incomplete coverage.

For the notebook task, include a long English/Chinese note, the collection/editor
relationship, both reading densities, draft retention through appearance changes,
save/reload, find/reopen and deletion cancellation. For the conversation task,
include an unfolding long answer, manual scrolling, source opening/closing while
output arrives, draft/composer continuity, narrow return and stopping/recovery.

selection among several cards, long/short content, local-save failure, keyboard
continuity and the reduced-motion equivalent. Select the relevant family only.

Record concrete observations of composition, type, hierarchy, material, feedback,
spatial stability and task continuity. Distinguish a reproduced product defect
from a locator/test-harness failure. Record how to reproduce a consequential gap
and the exact state, content and viewport where it occurs. Do not repair the app
or silently replace an original failed result.

Write REVIEW.md and a concise review.json with observations for every variant,
executed checks, actually viewed images/intervals, consequential differences and
unobserved dimensions. Explain design tradeoffs in observable terms. No aesthetic
score, universal winner, statistical significance, human-user acceptance or
target-device smoothness should be inferred from these samples. Behavior assertions,
captured frames and viewed frames are separate evidence. Research depth cannot be
inferred from appearance; process records are assessed separately by the maintainer.

End with your actual findings, remaining uncertainties and the output paths.
