# Default-deny construction — comparative execution study

## Question

Does the integrated mature-resource/default-deny method change actual resource
adoption, preservation of visual craft, coherent product quality and handling of
bounded originality, compared with the preceding complete method? Treat these as
separate questions. More adopted packages is not assumed to improve the result.

## Conditions and boundaries

- **A:** exact complete v1.18.0 installed runtime, from commit
  `dde8834c25046b0b73238f5f829500bfe8b40581`.
- **B:** complete frozen candidate runtime prepared by the coordinator before its
  participant executions.

Use a fresh independent Agent thread for each of the six task/condition cells.
Give participants only the assigned runtime, task, common environment and sources;
do not disclose the comparison, expected outcome, other products or author review.
Do not use participant subdelegation. The shared coordinator may prepare runtime,
source and dependency inputs but must not build the participant's final product.

| Task | Responsibility | Work ceiling, including full Skill reading |
|---|---|---|
| T1 | Complete local collection workspace and expressive surfaces | 22 minutes |
| T2 | Continuous card motion, material, long content and failure/retry | 18 minutes |
| T3 | Shared type inheritance, a specifically authorized identity mark and conflict presentation | 15 minutes |

All conditions in a task receive identical starter, source and task bytes. They
have the same host tools and optional external-resource access. Preinstalled
dependencies are environment support, not adopted implementation. An initial
source is a lead, not an evaluator-selected winner. Record actual timing,
interruptions, blockers and missing observations separately from the nominal
ceiling. There is one execution per cell; results do not establish a statistical
effect or equal machine load.

The existing T2/T3 products are authored repository fixtures, with their original
source disclosures preserved. T3 explicitly accepts the existing design for its
bounded work. Their availability does not establish that their design is universally
mature or that any added implementation is reuse. Inspect the actual relationships.

## Pre-execution registration

Freeze task text, starter files, source bundle and runtime digests before the first
participant receives them. Preserve that registration unchanged; annotate later
corrections without overwriting historical inputs. Record launch/finish facts and
actual prompts. If B changes after freeze, identify the tested snapshot and publish
the difference or repeat the affected test; do not relabel an earlier run.

## Observations

Review six independent outcomes without assuming that stricter policy improves
quality. Retain unsuccessful results and these possible counterexamples:

- A baseline already preserves mature craft and B offers no observed gain.
- B adopts more sources but the combined hierarchy, material or motion deteriorates.
- B correctly keeps a visual responsibility unresolved, with less implemented
  scope but more accurate claims.
- B over-blocks ordinary configuration/integration or widens a narrow authorization.
- Source installation survives but its defining mechanism is removed or replaced.
- Extra dependencies, global styles, duplicated state or rendering cost undermine
  otherwise useful resource adoption.

The review should inspect the final applications at the same viewports and the
relevant changing interactions. Record candidate-origin/source render, integration,
retained visual mechanisms, unresolved quality and actual functional behavior.
Distinguish the task's desired result from a merely runnable prototype.

## Comparison and claims

First anonymize and inspect products against their task, without method labels or
participant self-evaluation. Then examine source lineage, adaptation, recorded
choices and scope of originality. Use concrete findings for composition, typography,
material, motion and task continuity; avoid an automatic maturity score. Assess
engineering cost using actual dependencies, integration conflicts and observed
runtime behavior, without converting code volume into a quality metric.

The coordinator should retain participant source, meaningful captures/recordings,
outward explanations and exact reproduction commands. Captured files, actually
viewed material, engineering assertions, Agent judgments and human acceptance
establish different facts. A local experiment is evidence about these tasks and
conditions, not a universal design-quality guarantee.


## Common environment correction during execution

The initial source and runtime registration remains unchanged. Before final locale
verification, the coordinator's README preview exposed absent Chinese glyphs in
the test browser. The common [environment addendum](environment-addendum.json)
provides the official Noto Sans SC font through an external Fontconfig setting.
The same message is supplied to all six applications and all product reviewers.
The first three threads had already been dispatched; some preliminary font work
therefore occurred before the correction. Preserve that limitation when comparing
effort. No product design or frozen task/runtime input is changed by the addendum.

Dispatch and freeze times are recorded using the executor's host clock. Tool
ordering and source identities establish the recorded execution sequence; these
wall times are not asserted to be synchronized to GitHub's server clock.

## Post-comparison source correction

The original six-run registration and runtime B remain unchanged. Final semantic
review identified two unqualified original-work premises in the old worked
examples. The release qualifies those 3D/wordmark routes with W1 necessity and
actual asset-scoped authorization, retaining their craft instructions. The only
changed file and both exact texts/hashes are in
[final-runtime-delta.json](final-runtime-delta.json).

A separate fresh final-runtime execution is registered under `followup/`. It uses
the same T3 starter and task plus an explicit relevant-examples reading instruction.
It is a focused follow-up, not a replacement for a frozen comparison output or a
fourth matched task. The original comparison conclusions retain their original
scope. No participant application is repaired by the coordinator.
