# Mature foundations and default-deny construction — actual results

## Finding

The six executions show a concrete change in visual-source responsibility, but
**do not establish a general improvement in visual quality**. The new-method
collection workspace adopts a page/system foundation as well as a visual
component; the baseline adopts the same local visual component while constructing
the surrounding page itself. In the motion task, both preserve mature mechanisms,
but the direct-adoption result has softer card text and a larger runtime burden.
In the accepted-system task, both respect the narrow identity/comparison scope;
the new-method result handles continuing conflict updates and focus more clearly,
with a less compact mobile comparison.

These are observations about three tasks with one execution per condition. They
support the usefulness of explicit source accountability and the need to validate
integration. They do not show that stricter reuse inevitably produces better
composition, typography, motion or engineering cost. The counterexamples are
retained in full.

## What was executed

The unchanged [registration](registration.json) was frozen before dispatch, with
complete installed methods, identical task/starter/source bytes within each
family, and separate fresh Agent threads. Participants were not given method
labels, expected conclusions, other applications or coordinator review notes.
They could inspect the pinned optional source pool and research external sources.
The coordinator did not build or repair their final applications.

## Outcomes by task

### T1: broader provenance, mixed visual result

Both applications passed the independently exercised search, saved filtering,
save/unsave persistence, readable detail, browser-back/context restoration and
storage-failure/retry paths. Actual failure injection caused neither application
to lose the current session's selection or falsely claim persistent success.
Representative long titles wrapped without observed horizontal overflow. The
reviewer confirmed list scroll and title-focus restoration through actual controls.

A uses MagicCard's real surface and edge-light mechanism, Lucide icons and locally
loaded Instrument Serif/DM Sans, while its source record explicitly identifies the
page structure and type tokens as project-authored. Bootstrap Album was a visual
reference, not an adopted page implementation. B actually uses Bootstrap
Album/Blog structures, CSS and type relationships alongside the pinned MagicCard
source, with semantic theme configuration and focused integration changes.
This is the clearest observed difference in foundation scope.

The visual judgment does not simply follow that difference. The independent
reviewer found A's display type, restrained warm color, soft card light and
detail sidebar/body relationship more coherent. Its list description was only
12px, however, with 9–11px auxiliary text and Save text. B's description and
controls were easier to read at 16px/14–16px, while its card treatment and detail
organization were flatter. B placed ordinary save-success feedback below the
list, farther from the action; its error warning itself was clear and usable.

B also exposed two real source-integration conflicts. Bootstrap's important
border declaration initially hid MagicCard's transparent edge mechanism; its
default smooth root scrolling interfered with context restoration. The participant
repaired both before freezing. These incidents show why actual retained craft
must be checked after adoption. They do not show that merely importing a larger
foundation makes the product visually stronger.

Both products use the supplied sample collections. Their readable detail content
does not supply individually openable research references. B explains the sample
reference count more directly; A labels sample content in the footer. The study
does not certify the underlying research content as a real reference library.

### T2: actual reuse on both routes, with an integration counterexample

Both outcomes use the pinned Kokonut CardFlip v2 work. A makes a bounded vanilla
port of the substepped spring, seven thickness slices and angle-dependent
light/shadow/lift. It retains explicit button turns and does not claim the source's
drag/tilt/spin interaction. B integrates the source component through a React island,
retaining its fuller interaction mechanism and only adding localizable help and
dynamic reduced-motion settling. Vanilla business state remains authoritative in
both applications.

The independent reviewer exercised long mixed-language notes, saving delay,
actual storage writes, failure preservation, recovery, submitted-snapshot versus
new-draft behavior, return-to-edit focus, both viewports and changing theme/language.
Both preserved the ordinary note task in those paths. Seven rapid button reversals
finished on the expected face; sampled angle histories did not restart from zero
on each input. B additionally passed direct card Enter, Space and drag actions.

A's integrated paper treatment and card text were judged clearer. Its long-note
viewport measured about 197px high on desktop versus B's 150px; on mobile the
corresponding measurements were about 108px and 101px. B's card text appeared
softer than the adjacent form in desktop/mobile and light/dark observations.
A's mobile editing field also offered more writing room. These are concrete
perceptual/task differences, not a claim that every larger dimension is better.

This is a meaningful negative result for an unqualified direct-adoption story:
retaining more of the source implementation did not make the integrated reading
surface better. A's handwritten adapter contains recognizable adopted mechanisms;
it should not be classified as prohibited invention merely because the controller
was translated. Conversely, B's near-original component does not earn a quality
pass from source similarity. The current policy's adaptation/retention distinction
is necessary to interpret both outcomes correctly.

The source review identifies a possible relevant adaptation difference: A
compensates the resting face's depth transform while B retains the original depth
mechanism. This is not an isolated causal experiment proving the reason for the
softness. The observed defect remains a product result regardless of that hypothesis.

The review also retains an unresolved combination-state observation: in a long
automated sequence, both reduced-motion captures showed shifted card content.
Fresh-page checks using visible-coordinate clicks rendered normally. The report
therefore records the original captures and the successful narrower reproduction,
without declaring a confirmed reduced-motion defect or silently deleting the anomaly.

Continuous videos and rAF records exist, but reviewers did not watch the full
videos at natural speed. Ordered frames establish sampled states; they do not
certify subjective motion rhythm, displayed frame rate or low-end-device smoothness.

### T3: narrow authority works, with differing continuity and mobile tradeoffs

The task accepts the existing system and explicitly authorizes the folded-page
mark and, if needed, the missing local comparison presentation. Both applications
keep the editor relationship, use 14px placeholders with 15px entered text, retain
the control proportions and supply theme-appropriate marks. Neither repeats an
authorization request or uses the mark request to rebuild the ordinary page.
B explicitly records W1/W3 and distinguishes native dialog semantics from a
visual foundation. The actual primary foundation remains the accepted project.

Independent checks confirmed basic saving, simulated failure/retry, both version
choices, unresolved-conflict refresh recovery and remote deletion. In a separate
controlled delayed-save race, both kept the remote persisted value and preserved
the local text as a conflict. This later evidence covers that exercised sequence;
it does not retroactively turn A's earlier failed participant timing test into a
successful original run or verify every possible race.

For continuing B1→B2 remote updates, B updates the comparison to B2 and retains B1
history. A displays an update notification while still showing B1; the first
selection click refreshes to B2 and the second completes the choice. The reviewer
confirmed a protective check and did **not** demonstrate data loss, but the visible
text, notification and action meaning are out of sync. A also leaves focus on a
hidden dialog action after selection, with the next Tab returning to the top skip
link. B returns focus to the title and then the note body.

A's compact mobile comparison makes both versions/actions easier to see together.
B associates each action directly with its own version, but long content can push
the second version below the initial view and require both inner-text and outer
dialog scrolling. The reviewer actually reached and selected it, so this is a
comparison burden rather than an inaccessible control. Both retain a small wording
mismatch when describing remote deletion as a newly saved version.

Both participant research records keep future quotation-support relationships
separate from the existing title/free-text facts. They propose provenance and
stable identifiers rather than fabricate a graph. The blind product reviewer did
not read those research notes; the coordinator's source review covers their stated
scope separately. W2 and a source-only failure with no original-work authority
were not independently exercised by these tasks.

## Engineering cost and interpretation

| Observed cost | Meaning and limit |
|---|---|
| T1 B adds Bootstrap's broad stylesheet; final CSS is about 254 kB before gzip versus A's 37 kB | Wider mature scope has a real CSS cost. Both main JavaScript builds are about 399 kB; A also distributes local font files. No loading-speed benchmark was performed. |
| T2 B adds a React/Tailwind build; saved output lists about 265 kB main JS, a 9.6 kB business chunk and 38.5 kB CSS | Direct source use increases runtime/build responsibilities. A preserves the static entry with a bounded source-derived adapter. This is a tradeoff, not proof that either stack is always preferable. |
| T1 border and scrolling conflicts; T2 perspective-envelope adjustment | Supported configuration and focused adaptation still require observation in real content/state conditions. |
| T3 keeps the vanilla system and local persistence boundary | A closed exception does not require a new dependency or page redesign. It still needs actual interaction validation. |

Package names, imports and code percentages are not used as maturity scores. The
independent product reviews, source lineage and build records support different
facts. Their conclusions remain separate.

## Final source correction and separate follow-up

After the six runs, a separate semantic reviewer found two old worked examples
that still put original 3D/wordmark work directly after a visual reference. The
central policy already prohibited that shortcut, but the concrete examples needed
their own qualifying premise. The final release adds W1 necessity and actual
asset-scoped authority to those two passages while retaining their craft detail.

The original B archive and registration are unchanged. The complete final runtime
and the only changed file, `references/examples.md`, are identified in
[final-runtime-delta.json](final-runtime-delta.json). A separate fresh execution is
registered in [followup/registration.json](followup/registration.json), using the
final 37-file runtime and the T3 task with an explicit relevant-examples reading
instruction. The [completed follow-up](followup/RESULTS.md) preserves the accepted
system, records actual W1/W3 authority and delivers the local mark/comparison. Its
13px placeholder choice and absence of unresolved-conflict recovery after refresh
are explicit, as are its participant-run check boundaries and three coordinator-viewed
images. It is not counted as
a replacement, a matched extra comparison or proof that the original B runs used
the final example bytes.

## Limits of the evidence

There is one execution per task/condition and one independent Agent review per
pair, on a shared host with rolling starts. The methods differ in their full
instructions, not in a length-matched single sentence. The curated source pool
made good implementations readily available, although external discovery remained
open. This design cannot establish statistical causality, resource-exhaustion
behavior or universal compliance with the closed allowlist.

The first three participant threads had started before a missing CJK font was
corrected for the common browser environment; some preliminary font work occurred.
The correction and source identity remain in the environment addendum. Independent
T1 review also needed separate Vite optimization caches. Recording-tool paths were
not equally resolved in every attempt. These are disclosed environment limitations,
not selectively assigned product defects.

All applications were inspected in the provided Chrome with simulated viewports.
There is no real-device, complete screen-reader, cross-browser, long-term performance
or human preference acceptance result. A screenshot's existence is not a claim
that every pixel was inspected. The saved reports distinguish actual views,
measurements, assertions, recordings and missing observations. Full private Agent
execution transcripts are not part of the archive; actual prompts, assigned
methods, saved outward explanations, artifacts and inspection records are retained.

The justified release conclusion is a stricter and more explicit implementation
discipline with observed examples of broader source accountability and scoped
authority. Its success still depends on source selection, coherent composition,
careful adaptation and actual product verification. This study specifically rejects
using greater reuse scope or more retained code as automatic evidence of better UI.
