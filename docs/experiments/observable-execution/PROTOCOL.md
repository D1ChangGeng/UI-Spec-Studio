# Observable execution — registered comparative study

## Question and conditions

Does making consequential design work visible improve what an observer can see,
what the Agent actually does after an observation, and the resulting UI?
Evaluate these as three separate outcomes.

- **A / s8:** exact full v1.17.0 runtime and the common host communication rules.
- **B / v5:** A plus the [visibility module](visibility-module.md), linked from the
  entry. It strengthens event selection, early actual-result presentation and
  object-centered expression, while keeping the preexisting design methods.
- **C / k2:** the full frozen v1.18.0 candidate. It additionally connects disclosure
  to source/demo/trial/integrated identity, actual retained quality, material-gap
  correction and reinspection at the responsible design level.

All conditions already include adaptive formal SPEC granularity, mature-resource
reuse, perceptual/temporal inspection and evidence-guided action. A is existing
output under the same host, not an absence-of-output condition. B and C share
the intended event kinds and flexible expression; C strengthens the integration
with actual design responsibilities. This is an additive field study, not a
perfectly length-matched token ablation.

## Independent tasks and budgets

Each condition/task cell begins in a fresh Agent thread with no author conclusions,
other outputs or condition comparison in its task. No participant subdelegation.

| Task | Product responsibility | Maximum work window |
|---|---|---|
| T1 | Editorial collection workbench, mature pointer-responsive card surfaces, local save and detail flow | 24 minutes |
| T2 | Existing card, material/type and continuous front/back motion, failure/retry and return | 18 minutes |
| T3 | Existing accepted form, a smaller placeholder hierarchy with preserved text/control sizing | 10 minutes |

The ceilings include reading, research, implementation, outward messages and
verification. Same tasks, initial app bytes, resource availability, model settings
and browser environment within each family. Record observed elapsed time,
interruption and overruns; do not infer efficiency from a nominal ceiling.
Tasks run T3, T1, T2, with rolling starts as a participant slot becomes available
and the coordinator can dispatch it. T3 and T1 cells overlap; T2-C completed before
T2-A/B started because coordinator dispatch was delayed. There is
no claim that every family's three runs were concurrent or saw identical host load.
There is one execution per cell and no statistical replication or hidden second
attempt. Shared machine load and the common recording/host requirements are
limitations; nominal windows are not measured equal effort.

T1 offers exact MIT-licensed Magic UI source candidates and official demo links.
They are optional leads, not a required source or an assumed quality winner.
Sources fetched for research but unsuitable for standalone redistribution are
not included as a component bundle. T2/T3 begin with existing repository fixtures.
The bounded design brief governs whether broad discovery is useful.

## Contemporary outward evidence

The same team relay mechanism applies to all conditions. The participant archives
an exact commentary/final message immediately before emitting it and relays that
same text to the coordinator. The experiment-only recorder captures the app source
at that moment. The coordinator records actually received relays and checks the
text identity. Messages are not reconstructed after completion; planned messages
without a received relay remain unconfirmed.

The first coordinator receipts retained rendered text, which omits a terminal LF
in four messages. Their full text is equal after removing only terminal newlines;
the original exact message files and source snapshots remain unchanged. Later
receipts acknowledge the original text hash after the relay was actually received.

This mechanism samples actual outward design communication in delegated threads.
It is not proof that a human read the message or approved the result, and it adds
common recording overhead that could affect all conditions. Internal reasoning is
not published. Source snapshots and referenced media establish the result available
at the time; a later polished report cannot establish an earlier disclosure.
The received recorded messages are the audited sample, not a complete export of
private Agent threads or every host-visible tool result. The known unrecorded
T3-s8 startup is retained as a later report; completeness beyond the received sample
is not assumed.

## Review

Freeze outputs before review and do not repair participant products using review
feedback. Product reviewers receive anonymized applications and task briefs first,
with no method labels or participant prose. Operate real tasks and inspect actual
screens/continuous behavior at stated conditions. Review the outward transcripts
separately against contemporary source/media, then examine whether important
findings affected actual subsequent implementation or verification.

Compare meaningful relationships and concrete failure cases; output count,
word count, test count and record completeness are descriptive only. Distinguish
captured from actually viewed media, measured behavior from perceptual judgment,
and Agent review from human acceptance. Retain unsuccessful checks and outstanding
gaps. Report local observations without claiming general superiority, causal
certainty, real-device performance or universal research-depth gains.

## Frozen artifacts

The [registration](registration.json) identifies complete runtime and task hashes.
Input/starter identities, actual prompts, launch/finish facts, received relays and
replay snapshots are preserved with the run evidence. C must match the published
37 runtime files; a post-freeze method change requires a separately identified run
or an explicit limitation.

Registration was populated while T3 was already running, so this is not a fully
preregistered experiment. Two T3 starter hashes initially captured an edited file;
the [untouched initial record](registration-initial-record.json) and
[explicit correction](registration-correction.json) preserve that error. The
exact baseline and all three first-message source snapshots agree on the original
starter bytes. No participant application or result was changed by the correction.
