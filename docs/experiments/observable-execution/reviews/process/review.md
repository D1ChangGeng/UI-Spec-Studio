# UI Spec Studio：observable-execution 独立过程审计

审计日期：2026-10-30。范围：T1、T2、T3 的全部九次冻结运行。

## 结论

**本轮最有力的正面证据是：B/v5 与 C/k2 在复杂任务中，更早把可辨认身份的实际成果主动交到观察者面前。它们的实现并没有停留在展示。可是，A/s8 也有大量由观察进入实现、修正和复查的实际证据；本轮不能据此声称只有 C 完成了这种闭环，更不能由表达、截图或检查数量推导 C 的最终 UI 更好。**

三种结果应分别陈述：

| 结果维度 | 本轮可支持的判断 | 不能据此推出的判断 |
|---|---|---|
| 重要成果被主动展示 | T1 的 B 提前展示集成首版；C 先展示明确标为本地源码试验的候选对照，再展示集成首版。T2 的 B/C 提前附实际应用实图；A 在这两个复杂任务中主要文字报告，到 final 才给成果图或图的链接。 | A 没有进行研究、视觉检查或重要工作；更多消息意味着更多可观察价值；用户确实看过并接受了展示。 |
| 观察进入实际行动 | 三个条件在 T1/T2 都有源码检查点可核对的实质修正。C 的若干说明把材料身份、实际结果和缺口说得清楚，且有相应代码；B、A 也出现了同样重要的观察与修正关系。 | 展示本身造成了修正；只有 C 有闭环；更完整的描述证明更深的研究或更多设计工作。 |
| 最终 UI 品质 | T3 三组最终应用文件逐字节一致，是明确的相同实现结果。T1/T2 有不同设计与实现；需要独立操作及视觉审阅决定其得失。 | C 的早期展示更具体，所以最终 UI 一定优于 B/A；192 项断言必然比 39/43 项更可靠、更美观。 |

## 审计方式与边界

先读 `E/PROTOCOL.md`、各任务原文、原始 outward 消息与其源码快照，然后比较相邻快照、输入源码、最终源码、参与者检查脚本及结果；之后才阅读参与者自己的设计记录，以核对其解释。**未读 `PROCESS-REVIEW.md` 或 `RESULTS.md`；未使用作者结论建立判断，也未修改 Skill、参与者产品或原始证据。**

实际打开了 T1 的本地候选图、部分早期集成图，以及 T2 的 B/C 早期桌面和手机图，以核对所称对象是否确为候选或应用。它们只能支持这些画面的静态观察。本文不是新的端到端产品验收，没有重新运行九个产品，也没有完整播放其视频。对于参与者“已查看”的声明，区分其 outward/记录中的说明、保存的媒体，以及本审计实际打开的媒体；**保存了图片或视频不等于独立证明当时已观看全部内容。**冻结包没有完整的原始工具调用/图片查看日志，因此不能逐一核实所有观看声明。

本审计不要求每次运行都有某一组固定节点，不给每条消息打分。T3 的短小局部修正可以直接完成并交付；不因其缺少候选演示或中途截图而判为流程不足。

## 测试、动态结论与实际失败

### 存储边界的证据层级基本诚实

T1 三组的成功保存/刷新使用真实浏览器 localStorage，失败场景主要注入 Storage 写入异常。其 final 或记录明确说明了注入边界。

T2 三组的脚本确实向隔离 origin 写入填充数据，迫使原生 localStorage 失败，再释放填充项并从 UI 重试。脚本同时核对草稿保留与旧记录未被覆盖；没有在这组配额场景中替换 `Storage.setItem`。这是真实浏览器存储边界，但仍是实验主动制造的故障，不能扩展为真实设备所有存储失败原因的覆盖。

关键证据：A `participant-evidence.zip/verify.py`、`verification.json`；B `participant-notes.zip/verify.py` 与 `participant-evidence.zip/checks.json`；C `participant-notes.zip/verify_app.py` 与 `participant-evidence.zip/checks.json`。

### 数量相同或更多，不代表范围相同或品质更好

C/T2 的 192 项是八组条件下重复执行的一组行为断言；B 的 39 项、A 的 43 项组织方式不同。某些行为只在部分视口上完整跑，另一些条件主要跑布局与状态检查。报告应保留这些真实条件，不能把数字并排转成优劣分数。

C/T2 的全行为报告记录的是字号末改之前的样式哈希；末轮三个字号变化之后，`final-render-checks.json` 记录了最新样式哈希及八组正反面溢出/动作重叠复查。这是合理的定向复核，**不是对最终字节又完整重跑了 192 项**。A/T2 同样将 43 项检查与最后返回入口、标题换行的定向复查分开，`final-return-check.json`、`final-visual-check.json` 有对应源码哈希。B/T1 的最终 22 项是保留前段有效结果并完成局部续验的汇总，不应表述为一次从头到尾零故障运行。

### 动态证据仍是有限采样

T1 的光照证据包括自然输入、有序截图与部分时间记录。A 的 commentary 使用“逐帧查看”略容易让人理解为穷尽视频帧；final 收窄为七张采样帧，记录也明说没有连续播放或帧率结论。B/C 的 final 对采样、性能和完整播放范围限制得较清楚。

T2 的 A 有 99 张有时间记录的 screencast 样本及顺序图版；B 有自然时序翻转/反转截图和变换矩阵记录；C 有顺序帧及保存的视频。C 明确说视频没有逐段播放，A/B 同样未把截图当完整视频播放或目标设备帧率验收。应保留这一诚实限制：本轮支持已观察状态与采样过程，不能确认所有时刻的连续知觉品质、呈现掉帧、真机触摸或输入延迟。

尤其是 C/T2 的 `checks.json/episodes.face` 是目标 `data-face`，不是当前画面实际朝向；其“背面语义”断言在等待翻转后进行。A/C 的 `setFace()` 立即按目标面改 `inert/aria-hidden`，B 则依据 `DOMMatrixReadOnly(...).m11` 在动画过程中更新。**现有 A/C 终态断言不能证明中段可见面与语义同步。**这是本审计发现的覆盖限制，应交给独立动态产品检查；本文没有把源码推断扩大成实机已复现缺陷。

### 失败和中途修正应继续保留

- A/T1 的官网证书访问失败在 `sources-run.json`，后续成功访问另在 `official-demo-retry.json`；早期 outward 正确区分本地源码判断与官网实测。
- B/T1 的 `verification-run1.json` 保留 Playwright `Illegal invocation`，`verification-run2.json` 保留续验中的 `QuotaExceededError: test`。最终报告明确是故障注入/恢复表达式导致的测试工具问题，脚本修正后做局部续验。不能把它们删除后包装为无失败的一次执行，也不能把测试工具错误当产品缺陷。
- C/T1 的设计记录说明恢复测试曾因返回原生函数产生工具错误；最终成功结果和修正脚本在包内，但未见与 B 同等独立保存的原失败结果 JSON。能确认其主动承认该失败，不能从冻结文件完整复原该失败调用。
- A/B 的 T2 长文本 End 键立即判断遇到原生滚动时序，最终脚本改为等待实际滚动。A 的设计记录、B 的 outward 和 `check_scroll.py` 记录了这一调整；原失败的完整工具输出不在本次包内。应写为测试时序修正，不能算 UI 缺陷修复，更不应悄悄当从未失败。

九组已收到的 outward 样本没有出现因审美、参考资源选择或中途结果而新增的用户审批门槛；各组均继续实现到交付。参与者记录中“方向暂定/未获 owner acceptance”是在区分实施判断和用户验收，不是等待用户才能继续。

## 证据完整性与方法限制

1. **源码证据可复核。**独立重算全部 46 个消息源码包成员哈希，与消息 JSON 内的 `source_files` 一致；九组首消息源码与 `app-initial.zip` 一致，final 消息源码与 `app-final.zip` 一致。按任务比较，三组输入分别一致。结果在本目录 `integrity-check.json`、`family-identities.json`。
2. **收到 relay 的含义有限。**各条正式消息有 coordinator receipt：早期四条仅差终端换行，两条早期文本精确相等，后续是收到并审阅后对原文本哈希的确认。哈希确认不是第二份完整文字副本。它证明协调者记录了收到的消息，不证明人类用户阅读、理解或批准。T3-s8 另有一条后来报告的未记录启动语，receipt 正确标为 retrospective/unrecorded；没有将其补算为当时确认收到的消息。
3. **当时媒体没有单独冻结/hash。**recorder 只归档 `app/`，未将截图/视频与每条 outward 一起封存。后来 `archive-index.json` 的媒体哈希只能固定最终包，不能追溯证明展示时的媒体字节。存在具体例子：C/T1 `message-004` 引用的 `desktop.png`，如今归档背景像素是 `(18,19,19)`，对应后续 `#121313`；同号源码仍是 `#111412`。其 DESIGN 也明确通用截图名后来重捕获。因此可以确认该消息当时附了这一图路径、当时有集成源码；不能把当前 `desktop.png` 当成当时原始画面的像素级证据。颜色修正本身有源码前后证据支持，不依赖这张被复用的文件。
4. **时间是观测跨度。**`timing-and-display.json` 记录首条归档消息至 final 的跨度：T1 A/B/C 约 21:44、21:06、13:17；T2 约 16:52、10:11、10:07；T3 约 5:15、4:13、4:02。它们不是精确启动时间、净工作时间或 token 成本。不能以此宣布效率倍数，亦不能仅由跨度短于预算证明所有启动前工作都在上限内。
5. **不是完全预注册。**协议说明 registration 在 T3 已运行时才填完，两个初始样式哈希误抓了编辑后文件。初始记录及 correction 保留错误。重算的三个初始包与各 first-message 源码支持更正后的相同输入；该更正没有改变参与者产品，但不能重新包装为事前完整注册。
6. **只有每个条件/任务一次执行。**条件为累加设计，B/C 不只是同长度词句替换；共享环境、录制开销、开始顺序及宿主负载并不完全相同。本审计未把实际执行模型设置/内部读取行为当作已由源码包验证。没有重复样本可估计稳定效果，也没有用户接受或理解效果数据。
7. **过程包不能代替独立产品审阅。**源码和检查点能判定实施身份与变化；通过的脚本能确认其具体断言。静态图、文字和次数不足以决定最终视觉层级、可操作性或连续运动品质的整体排名。T3 相同字节是例外，可直接确认同样实现。
