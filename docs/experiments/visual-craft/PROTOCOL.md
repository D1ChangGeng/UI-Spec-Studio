# Actual visual-craft adoption experiments

## Status and purpose

**This protocol is prepared, not executed.** The three task families below are
not three completed Agent runs. Independent execution is unavailable in this
maintenance session: the connected ACS project request returned a disconnected
tunnel. Source reviews, deterministic tests and the separately reported
maintainer application cannot substitute for the requested independent tasks.
The [status record](../../evidence/v1.16.0/experiment-status.json) retains this boundary.

The question is whether additional craft-based discovery and selection guidance
changes real Agent behavior and the resulting interface, not whether the output
mentions enough libraries or fills a record. The exact baseline is v1.15.0,
commit `a89091dfa5754f98b79655c684f978f24fd92716`; it already contains substantial
reuse-first and evidence methods. Do not weaken that baseline.

## Matched inputs and execution

Compare the baseline with the delivered candidate in fresh, isolated sessions.
Use the same task prompt, project source, permitted reference access, asset
permissions, model/version, harness, tools and resource limits. Freeze the actual
candidate commit and installed-file hashes before execution. State permitted
network/browser conditions, blocked resources and permitted human assistance.
A prepared prompt, locally written implementation, replay or mocked Agent is not
a fresh Agent run. Do not leak the candidate instructions into the baseline.

If multiple models or harnesses are used, treat them as separate strata. Log
start/end, tool actions and their returns, source identities, files actually
adopted, configuration/adapter changes, real rendering and tested conditions.
Preserve failed searches, rejected candidates, incomplete work and interruptions.
Redact credentials and private information before publishing trace excerpts.
Execution budgets define comparability, not a universal quota for UI research.

## Three ordinary task families

### 1. Complete product experience alignment

Task: build a usable personal research conversation product with familiar
conversation initiation, attachments, source reading, history continuation and
responsive behavior. Use supplied reference access and representative long
content. Keep a clear independent identity while targeting comparable craft.

Look for task-derived coverage challenged by actual product evidence, source
research at page/block scope before broad implementation, real adopted visual
structure beyond primitives/icons, and intact usage through pending, failure,
return and content growth. Inspect the completed task, not only the empty screen.

### 2. Expressive professional workspace

Task: improve a populated working interface with a distinctive editorial or
spatial identity without changing its business behavior. The brief explicitly
permits strong typography, photography, graphical material or motion in daily
work, not just a marketing header. Both variants receive the same asset rights.

Observe whether product type prematurely suppresses the target, whether varied
cross-domain references shape the chosen relationships, and whether actual
mature resources are integrated coherently. Test repeated work, readable holds,
quiet/reduced-motion conditions, theme/content variants and cumulative cost.
A busy composition is not automatically expressive success, nor is restraint
inherently a failure; inspect the agreed target under actual use.

### 3. High-value local component or motion

Task: improve one consequential object such as a reading/result card, multi-file
composer or draggable detail sheet. Preserve the surrounding accepted design and
state authority. The input does not prescribe a library or ask for a rewritten
effect. Include a low-impact, already-supported variant as a convergence control.

Observe whether the Agent translates intent into mechanisms and search questions,
looks beyond familiar sources when needed, inspects genuinely different options,
uses original demos and actual local trials, and adapts through public controls
before rewriting internals. Distinguish authored motion, direct input and real
service completion. Unnecessary research on the supported variant is a cost.

## Independent review and separate conclusions

Blind output reviewers to version/group when feasible. Review the same tasks,
content and view conditions. Keep disagreements and uncertainty. Record:

- **Research behavior:** which sources were actually discovered and observed,
  which new observation changed a choice, and what remained inaccessible.
- **Actual adoption:** source/configuration/implementation identity and what
  visual relationships survived. A dependency list or borrowed idea is different.
- **Perceptual result:** hierarchy, reading rhythm, surface/light, state detail,
  spatial stability, motion continuity and coherence in populated use.
- **Engineering result:** exercised functional, accessibility, performance and
  cleanup assertions, with scope and device conditions rather than inferred quality.
- **Efficiency/adaptability:** actual tool/time/rework cost, deliberate custom
  scope and different suitable visual directions across briefs.

Do not replace these with resource counts, reuse percentages, library popularity,
an arbitrary aesthetic total or unit-test counts. A before/after improvement can
be described for the exact observed interface; causal or general conclusions
need repeated matched tasks and independent review. Keep completed-task findings,
missing evidence, user acceptance and all failed runs separate.

## Relation to current maintenance evidence

The [card application review](../../evidence/v1.16.0/application-review.json)
reinspects a previously prepared exact-source project, compares stationary light
with a moving plane, adjusts the host layout and exercises explicit browser
assertions. It is useful implementation evidence for that local object. It does
not answer the complete-product experiment, the whole expressive-workspace
experiment, independent Agent effectiveness or measured development-time savings.
