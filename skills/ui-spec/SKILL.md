# UI Spec Studio

Organize **Product UI Experience Alignment** through **Intent-Grounded Experience Research & Evidence-Driven UI Design**: understand the intended experience, set a high perceptual taste bar, discover mature visual foundations widely, compare meaningfully different candidates, adopt and harmonize resolved craft, and verify actual use—with or without a user-named reference. Own understanding, research, selection, implementation and verification through reviewable increments; the user supplies intent and evaluates results, while observed products and mature resources calibrate judgment under this product's actual conditions.

### Core Design & Craft Loop

Run this closed loop within every substantive design increment, returning to any earlier step whenever evidence warrants it:

```text
Intent & Taste Bar → Wide Multi-Tier Discovery → Meaningful Comparison → Local Trial → Deep Reuse, Harmonization & Craft Upgrade → Pixel/Temporal/Taste Critique & Polish
```

Apply the same discipline across product UI, UI SPECs, `README` files, documentation, diagrams and visual media. Keep **working products**, **representative product demonstrations** and **authored visual work** at their own realization and evidence boundaries; a static showcase or fixed-stage demo never certifies an interactive product.

## Start from mature design work

**Original UI construction is prohibited by default across all visible UI design responsibilities.** Mature external implementations and validated reusable project resources carry the normal foundation for pages, layouts, containers, surfaces, backgrounds, components, typography, icons, decoration, assets, states, motion and interaction effects. Original construction is never a routine fallback. The [sourcing policy](references/component-sourcing.md#default-deny-original-ui-construction) governs this boundary.

- **Pair theory with real ecosystems.** Theory explains quality, fit and tradeoffs; resource knowledge exposes concrete work that can carry those qualities. Seek the **highest appropriate reuse level**: a coherent product/page template or design system, then a substantial layout or functional block, then the components, primitives and effects needed to complete it. Judge **Reuse Scope** and **Visual Completeness** separately—headless primitives, icon packs and drawing engines supply functional foundations, not page composition, typography, surface material or motion craft.
- **Discover widely and reject generic defaults.** Discover suitable external mature work first across elite live products, curated high-craft registries, specialist engines/OSS codebases and independent type/icon ecosystems rather than settling for stock defaults or the first convenient package. Assess the project's existing mature work alongside external candidates by observed quality, product fit, continuity and total integration cost; a better-fitting validated project source can remain. Consult the [resource catalog](references/resource-catalog.md) as an open starting map, never a closed supplier list or quality ranking.
- **Execute deep reuse and source-preserving craft upgrades.** Agent-authored code may adopt, configure, compose, connect, de-template, harmonize tokens, isolate CSS cascades, repair rendering defects and adapt mature work—preserving the source's defining proportions, typography, material, state and motion relationships. New business wiring, responsive connections and compatibility fixes are ordinary engineering; silently replacing defining relationships with hand-built containers, styles or effects is unauthorized original construction. **Visual Provenance Obligation** attaches to design responsibilities (a coherent page, block, component family or validated token system), not to every DOM element.
- **Apply the closed W1–W3 allowlist for genuine originality.** Original visual work requires one of the [closed W1–W3 exceptions](references/component-sourcing.md#closed-original-construction-allowlist): **W1**, explicitly requested unique identity or art; **W2**, demonstrably unmet product-specific expression; **W3**, a necessary narrow extension that mature implementations cannot supply. Establish actual need, relevant research, inability to reuse, exact original scope, retained mature foundation, actual scoped user authorization and verification boundary. A general request to build, continue or finish does not authorize an unspecified W1–W3 exception; reuse existing authorization when already present, and surface a remaining exception only after advancing independent authorized work.
- **Never substitute custom work for a source gap.** A screenshot, understood technique, unsuccessful search, inaccessible demo, apparent simplicity, convenience or familiar stack never authorizes reconstruction. A complete user-supplied or confirmed design supports faithful design translation within its specified scope (not invented missing design). Temporary technical probes answer explicit research questions and remain provisional until replaced by mature work or covered by an authorized exception. **When no qualifying resource or authorized exception exists, preserve the unresolved responsibility rather than substituting lower-quality custom UI**—continue discovery, adjust reuse scope or supported composition, run bounded trials, pursue normal authorized user assistance when access is blocked, and advance independent work.

## Choose the operation

Infer the operation from natural language rather than waiting for literal commands. `Continue` resumes active work; `approved, continue` records approval for the identifiable reviewed scope and advances.

| User intent | Operation | Working outcome |
|---|---|---|
| Begin or adopt a UI effort | `init` | Complete goal, current foundation, revisable candidate SPECs and a justified first increment |
| Explore or resolve an important direction | optional `shape` | Reasoned experience/aesthetic direction, reference craft breakdown and, where useful, a bounded probe |
| Continue, add, refine, consolidate or repair | `iterate` | Progress or complete the active formal increment; start a new SPEC only for a distinct cohesive objective |
| Inspect existing quality, craft or coverage | `audit` | Dual-track functional/continuity + taste/craft-retention findings; repair and recheck within authorized scope |
| Connect approved experience to real behavior | `finish` | Real integration preserving adopted craft, design/product regression and accurate handover |

`shape` is optional inside any round or as a standalone exploration request; an established direction proceeds straight to `iterate`. Explicit analysis-only requests return decision support; implementation requests move into runnable code once direction is sufficiently supported.

On session or engineer re-entry into an ongoing product, establish the **Continuation Baseline** before editing code or restarting broad discovery by reconciling `Overall Product Goal`, `Current Design Model` and live `Current Product UI` ([re-entry and handoff](references/workflow.md#re-enter-and-hand-off-across-sessions-without-losing-direction)). Inherit settled commitments whose operating conditions still hold without re-litigating resolved direction; reopen a settled decision only on concrete changed user intent, changed operating/contract conditions or observed quality failure.

### Keep four working objects distinct

| Object | Responsibility |
|---|---|
| **Overall Product Goal** | Preserve the complete intended experience, capabilities, art direction, quality bar and constraints across iterations. |
| **Current Product UI** | Maintain the real accumulated pages, components, assets, shared systems and behavior that new work inherits, extends, adapts or revisits. |
| **Formal UI SPEC** | Own one cohesive design objective, its necessary experience relationships, an operable/renderable result and corresponding verification. |
| **Internal Research & Implementation Work** | Search, observe, compare, trial, implement, critique, repair and recheck as often as needed to fulfill that SPEC without spawning new formal iterations. |

Choose each formal SPEC boundary through the [minimum sufficient experience closure](references/analysis.md#choose-a-bounded-increment): include the coupled objects and relationships needed to understand, realize and judge one quality goal while keeping enough focus for deep work. A page, component family, background, shared type system or continuous interaction holds equal formal standing; area and file count do not decide scope. Explicitly recommend keeping, splitting, merging or redrawing a boundary as evidence develops—retaining the full goal, unresolved quality gaps, change reason and current responsibility across repartitioning. Across multi-month evolution, govern candidate and past increments as a living horizon (`candidate`, `active`, `completed`, `superseded`, `consolidated`, `retired`), sequence shared foundations and representative anchor slices before broad rollout, and apply [horizon governance](references/analysis.md#govern-the-multi-spec-horizon-and-retire-obsolete-scope) whenever consolidating, superseding or retiring scope so valid user task paths, transferred or closed obligations and dead UI removal stay explicit.

Coordinate all **nine experience dimensions** (product/interaction model, visual direction, visual assets, content & typography, spatial composition, components & states, motion continuity, performance engineering and operational UX) together. Infer the primary interaction model from what users do first, the object they work on, the repeated action/result loop, how they resume and where outcomes live—keeping product model distinct from visual theme. Treat **visual assets** (marks, icons, fonts, imagery, 2D/3D, dynamic visuals) and **product language** (user vocabulary, voice/tone, state copy, localization, factual authority) as first-class design material that shapes composition from the start—never late filler. Preserve explicit artistic requirements alongside task usability; professional software does not prescribe visual restraint.

### Choose the next action from evidence maturity

Judge coverage breadth, inspection depth, temporal completeness, relevance and reliability together (`references/verification.md`, `references/evidence-actions.md`). Converge on answered design questions, never on elapsed search effort or the first convenient candidate:

- **Continue research** when an unresolved issue could change the interaction model, taste/art direction or mature-resource choice, or when an unexamined direction could close a material quality gap.
- **Run a bounded local trial** when target quality and a candidate are credible and current-project fonts, content, theme or state conditions can answer fit. Keep the assumption and falsifying observation explicit.
- **Expand implementation** when defining qualities and candidate fit are supported, adaptations are clear and remaining gaps stay bounded. Reopen the affected decision whenever integrated evidence changes it.

At handover—both at completed increments and at interrupted mid-SPEC pauses—present both the `Current Design Model` and a concise conversation summary: working preview/entry path, distinct per-scope maturity facts (**implemented**, **visually inspected**, **owner-approved**, **connected**, **verified**), explicit separation of temporary probes, local trials and integrated UI, consequential choices and adopted sources, representative visuals/episodes, executed checks, active blockers/open obligations, approval scope and the single next concrete action. Keep project preferences local, and preserve reusable lessons as *problem, mechanism, applicable conditions, editable realization and observed result*.

## Non-negotiable invariants

1. **Visual provenance, acquisition, adoption and craft retention stay separate.** Track target reference → candidate original demo → local project trial → integrated UI at their own boundaries (`references/component-sourcing.md`, `references/verification.md`). Dependency installs, copied files, code volume and passing DOM assertions never prove retained visual craft. Before expanding a consequential component or structure across the product, verify it in a local trial with current fonts, content, themes and states; preserve valuable mechanisms through configuration and source-preserving adaptation, and repair concrete integration losses (font fallback, clipped lighting, resting 3D text blur, broken spacing or focus regressions) at the responsible layer. When upgrading shared tokens, shells or mature component families across large products, roll out in [staged waves](references/component-sourcing.md#migrate-shared-foundations-across-existing-surfaces-in-stages)—validating a representative anchor slice first, keeping coexistence bridges strictly bounded under W1–W3, verifying dependency-scoped seams and extremum consumers, and decommissioning legacy foundations cleanly.
2. **Real viewing, taste calibration and temporal inspection govern quality claims.** Apply **Observe → Interpret → Evaluate → Decide → Implement → Inspect → Refine** at intended scale: whole surface → relationships → details → whole (`references/principles.md`, `references/verification.md`). Observe complete time-bounded episodes (trigger → first feedback → progression → settled state → reversal/interruption/recovery) rather than isolated stills. Assess **experience validity**, **expressive completion**, **source fidelity** and **perceptual quality** independently. Even when functional checks pass, audit rendered output for flat, generic, cramped or inconsistent multi-source craft and upgrade before delivery.
3. **Observable design execution separates disclosure, review and approval.** Surface consequential facts in the conversation as events arise—formal scope target, research finding, resource choice, first reviewable result, material mismatch and formal delivery—via [event-driven disclosure](references/workflow.md#make-consequential-design-work-observable), using the same current facts as project records. Always identify whether shown material is a Target Reference, Candidate Demo, Local Trial or Integrated UI. Disclosure makes work visible; review examines it; approval requires an actual decision with identifiable scope. Continue authorized routine work autonomously after disclosure; ask for user choice only on unresolved high-impact direction, material commitment changes, W1–W3 exceptions lacking authority or external actions. Honor explicit delegation and label provisional assumptions on `one-shot` work.
4. **Multiscale evidence, four responsibilities and neutral inspectors.** Maintain L0–L5 coverage, decision traceability and gap-to-action discipline across consequential work (`references/evidence-map.md`, `references/evidence-actions.md`); **a schema or new document is optional**, while inspectable evidence relationships and commitment boundaries are required. Allocate exploration depth by design impact, uncertainty and plausible improvement (capabilities, never quotas). Keep **four responsibilities** separate: the **Design Evidence Map** holds current understanding; the **Structural Coverage Inspector** reports literal field/ID/file facts; **Agent Design Judgment & Execution** determines applicability, sufficiency and next action; **Verification & Acceptance** independently validates real renders, behavior, performance and owner decisions. Maintain **Current Design Model → Meaningful Revisions → Evidence Archive** proportionally to the active product and its open obligations: [compact closed history](references/evidence-map.md#compact-active-records-without-evaporating-open-obligations) into `Meaningful Revisions` and cold `Evidence Archive` without ever dropping open Visual & Craft, Provisional Probe & Migration Bridge, Integration & Contract or Verification Scope Debt across compaction or SPEC repartitioning. Optional inspectors (`scripts/check_manifest.py`, `scripts/check_design_evidence.py`) are strictly read-only and neutral—exit `0` means inspection ran, never design readiness, quality or approval.
5. **Main-agent authority governs delegated work.** When using auxiliary specialists (`ui_researcher`, `ui_integrator`, `ui_challenger`, `ui_experience_observer`), the main agent retains the complete product goal, formal SPEC, pivotal visual judgment, final mature-resource selection, whole-product integration and acceptance (`references/delegation.md`). Delegate complete questions in natural language, directly view pivotal returned evidence, enforce non-overlapping writes and GUI isolation, and absorb findings into one Current Design Model. Without compatible subagents, execute the exact same method directly.
6. **Source authority, host boundary and delivery honesty.** Product contracts, access rules and accessibility obligations govern valid behavior; accepted decisions govern preserved design; code establishes engineering capability (visual inheritance still requires acceptance or fit evidence); external references stay reference data with checked licenses and rights. When external engineering commits, hotfixes or API/permission/error contract shifts land between rounds, reconcile them by causal layer via [ongoing engineering drift](references/integration.md#reconcile-ongoing-engineering-and-contract-drift-between-rounds)—keeping compatible changes without blanket re-audits, adapting honestly to authoritative contracts, preserving functional/accessibility hotfixes while repairing degraded visual craft or provenance on top, and scoping pivots to affected objects. Keep Overview, Design Detail and Execution & Assurance aligned in both project records and conversation handover, preserving sensitive data inside authorized destinations. Changes to an installed or shared skill follow explicit maintenance authorization; this is knowledge maintenance, not model training or autonomous modification of its host. **The host controls activation**, tool access, context retention, compaction and execution—state missing capabilities (such as absent image viewing or network blocks) precisely, keep unverified dimensions open and advance all supported independent work.
