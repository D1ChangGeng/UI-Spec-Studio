# Design decisions and resource map

Use only the portions needed for consequential choices, or equivalent existing
records. Keep representative evidence and decision changes rather than a search log.

Use these same facts for [event-driven conversation output](../../references/workflow.md#make-consequential-design-work-observable).
Show consequential findings and first meaningful actual results while they can
inform the work; identify reference, original demo, local trial or integrated UI
and connect important gaps to the next action. Select useful portions rather than
copying the whole template or creating a document for each event. Showing a result
does not establish user review, approval or completion of its quality obligation.

## Product and scope

Task and audience; requested redesign scope; current business/engineering facts.
Primary working object, first meaningful action, repeated loop, continuation and
result location. State the target experience with or without a named product
reference. Expand names or style descriptions into the relevant task, surface,
state and relationship. Separate observations, inferred model and open intent.

Keep current-user intent, audience conventions and actual product practice distinct.
Identify the version, platform, role and conditions relevant to the target experience.

Keep the complete product goal and current product UI identifiable. For the active
formal SPEC, state the coherent experience objective, qualities it owns, necessary
connected objects and why this scope can be researched, implemented and reviewed
well. Distinguish research/observation, primary implementation and integration/regression
scope. Link revisable candidate increments and inherited decisions where useful;
one page can receive several formal increments and one increment can span objects.

## Research question and evidence plan

Link the experience hypothesis to important parts, states, journeys and relationships.
Explain which text, rendered view or interaction can answer each consequential
question. Keep source statements, actual observations, interpretations and missing
evidence distinguishable. Name a finding that could change the current choice.

Record the significant discovery, its effect on understanding and the next useful
search, observation, comparison or trial. Independent origins and materially different
design relationships establish breadth; repeated listings retain their common lineage.

## Direction and authority

Recommended interaction model and visual direction; relevant mature product
flow links, inspected scope/date and transferable conventions. Name meaningful
alternatives and differences in actual use when a significant choice is open.
Record user choice, explicit delegation or provisional recommendation with its
source and affected scope. A preview option selection records only its stated scope.

Separate required task behavior, explicit aesthetic goals and revisable conventions.
Name functional, cross-domain expressive and implementation source roles. Show
consequential art directions with actual material and comparable completion;
identify what stays familiar, what changes and how the theme persists in core work.

## Foundation comparison and selected granularity

Concrete mature page/system/block candidates, source/demo/revision, actual observed
states, meaningful episodes and evidence. Explain the selected level, valuable design relationships
inherited together, local trial and meaningful alternatives. Identify the implementation actually
adopted and the mechanisms preserved. Classify code reuse, configuration, composition,
design transfer and original work accurately; give the evidenced gap for custom common UI.

Keep the design reference and implementation resource identifiable. Record the
research question, useful clue/action and conclusion: observed phenomenon,
likely perceptual effect, underlying relationship and what this product inherits.
Attribute evidence to its carrier page, player, depicted product UI or displayed
work; retain edited-demo or actual-operation context where it changes the claim.

Compare alternatives under corresponding content, scale, theme and state. Explain
the competing strengths, the evidence behind the current preference and unresolved
tradeoffs. Preserve a promising unexamined direction when it could close a quality gap.

Record a source or trial finding that changes the proposed SPEC boundary, when
consequential: a mature mechanism worth adapting together, a newly necessary
cross-component relationship, or independent demanding goals worth separating.
Retain the complete target and original open findings through that revision.

## Reuse assessment

Preserved functional contracts and constraints. Existing visual candidates and
what makes each worth retaining, adapting or replacing against the target.

## Surface and resource selection

| ID / surface / state / dimension | Intended outcome and product-pattern reference | Exact implementation source / variant | Choice, reason and reuse depth | Adaptation and implementation/preview location | Evidence, date and current status |
|---|---|---|---|---|---|

Consider product objects, layout/navigation, content/typography, components, assets,
feedback, motion, runtime readiness and operating work as applicable.
Shared IDs can serve multiple pages. For native, authored or retained work,
identify the actual source and fit rationale. Link the exact source and demo when
external work is selected. Use an existing equivalent record instead of duplicating it.

Start candidates while direction is open. Reconcile studied, compared, trialed,
actually adopted and verified status with real code/assets and observed conditions.
Owner approval remains separate. A consequential trial uses current content, type,
themes and states before wider integration. Detailed notes may hold rights, versions,
modified mechanisms and maintenance ownership; reuse is assessed by the responsibilities carried.

Link important choices to a visible fact, likely perceptual effect, explanatory relationship
or hypothesis, product fit and actual implementation decision. Retain representative viewed
frames or time ranges and their display/crop/zoom conditions. Follow consequential details
back to their region, neighboring elements and whole-page effect. Inspect the reference, original resource demo, local trial and
integrated result separately; new evidence can reopen the choice. Retain quality
gaps, their responsible layer and any explicit decision changing the target or scope.

## Review and continuation

Working preview and source; inspected views, states and tasks; resulting changes;
remaining high-impact choice; approval source and acceptance evidence; next useful increment.
For motion-dependent decisions, identify the observed interval, trigger and
endpoint and which temporal questions remain open. Distinguish media acquired,
actually examined content and conclusions it can support. Record sufficient,
partial and missing evidence by decision impact; carry remaining questions into
the runnable slice and re-answer them under current product conditions.

Choose further research, a bounded trial or broader implementation from current
evidence maturity. Consider breadth, depth, temporal coverage, relevance and reliability
together. State which open question could overturn the decision and how the next
action will resolve or contain it. User approval keeps its actual scope.

## Asset production and placement

For identity-bearing or other consequential visual assets, link the shared asset ID
to its purpose, source/permission, editable master, production route, export
variants, delivery/placement and actual review. Use the asset record or existing
project equivalent. Keep visual approval, usable file delivery and runtime
verification scoped to their evidence.

## Content and language decisions

For consequential content, link the user question, surface/state, factual authority, localized wording, typography role and observed result. Reference the existing product content record or optional [content template](content-decisions.md). Keep routine strings in their component/content source.

## Runtime and operating decisions

For consequential choices, connect the intended sequence to preparation, validity,
resource cost, authoritative completion and recovery. Link relevant content/template
ownership, override behavior, role information and batch scope. Record measured
conditions and observed outcomes where evaluated; routine implementation stays in code.

## Multiscale map — use the current project record

Keep **one authoritative record**. The rows below are an expandable guide, not a
required inventory for every task. Important decisions must retain their evidence
relationships; this file and the JSON profile are optional representations.

### Overview

Intended experience and scope; user tasks; relevant reference versions/platforms;
important L0 goals, L1 journeys, L2 pages, L3 regions/components and L4 qualities;
L5 realization/check links at every useful scale. Identify shared objects once.
Link states/episodes, usage conditions, dependencies and evidence rather than
copying the object into each page's record.

Show the current product, active formal SPEC and useful candidate increments beside
the complete goal. Link each formal increment to its relevant objects, quality
responsibilities, inherited work and important dependencies; the page hierarchy
does not define its boundary. Keep research, implementation and regression scopes
identifiable without duplicating the underlying object/decision records.

### Coverage challenge

| Discovery from user tasks or observed reference | Evidence and conditions | Include / exclude / open, with reason | Affected object/decision | Next evidence route |
|---|---|---|---|---|

Check what the initial inventory missed, including relevant return/recovery,
content extremes and alternative device behavior. Exclude irrelevant reference
features explicitly rather than importing an entire product. Keep uncertain
scope open with a concrete question. Explain inheritance from verified families.

### Design Detail — a consequential decision unit

- **ID, linked objects and purpose:** which experience or perceptual quality matters?
- **Question and falsifier:** what is unresolved, and what discovery could change the choice?
- **Evidence and observation:** exact source/role, inspected portion or interval,
  state/condition/revision, actual finding, source assertion, inference and missing evidence.
- **Judgment and alternatives:** relationship creating quality, applicability,
  materially different options, comparable completion, reasons and tradeoffs.
- **Chosen/provisional implementation:** actual resource/variant/configuration,
  original demo, local trial, retained mechanisms, adaptation and source/asset location.
- **Claim-specific verification:** object, condition, method, observed result and
  evidence; keep visual, temporal, task and engineering findings separate.
- **Remaining gap and action:** dependent scope, concrete next operation and
  outcome that would close or revise the question.

For a routine inherited change, these relations can fit in a few sentences.
For a defining asset or complete product, expand the necessary visual and temporal
detail. Unknowns and pending trials remain explicit rather than invented.

### Execution & Assurance — the same decisions

| Decision/object | Research facts | Trial/adoption and actual locations | Scoped checks and current revision | Owner approval/exception | Open gap, dependency and next action |
|---|---|---|---|---|---|

Acquired, observed, compared, trialed, adopted and verified are scoped facts,
not a single global completion score. A source can be rejected after observation;
an adopted component can fail a state. Owner approval requires its own source
and scope. Keep historic results and reopen affected claims after changes.

Show the actual preview and representative inspected evidence alongside these
views. Keep long search logs behind useful links. The optional JSON profile and
checker provide structural feedback only; they do not establish that research
occurred or that the interface has mature visual quality.

In the conversation, present the important scope decision, resource comparison,
actual product result and remaining gap with proportionate depth. Use the same
current information as these views. Keep internal evidence classifications in the
design record; product copy and layout serve the end user's task. State whether
the deliverable is a working product, representative demonstration or authored
visual work, and identify unfinished behavior honestly.

### Action checkpoint

Before a consequential expansion, name which critical gaps still affect that
scope. Choose the next evidence-producing search, observation, comparison, local
trial or repair and state what would change the decision. Continue unrelated
supported work; a reversible probe stays explicitly provisional. After acting,
link the resulting evidence and explain the actual change to the decision.
Use [the action rules](../../references/evidence-actions.md) rather than treating
this template's completed fields as permission to advance.

## Current model and meaningful revisions

Keep the current goal, active choice, actual adopted resource, implementation link,
conditions and remaining question identifiable. Update the current judgment when
new observations justify it. Do not present a replaced resource as still adopted.

| Meaningful change | Why / actual new evidence | Objects and conditions affected | Current judgment | Prior record / original evidence |
|---|---|---|---|---|

Keep raw media, detailed traces and old records in the Evidence Archive; link them
rather than duplicating them in every view. A previous successful single-line check
can remain valid historical evidence while a new attachment condition needs review.
No global revision string automatically invalidates unaffected findings.

For a changed formal boundary, retain the original goal and finding, the new
evidence/reason, affected increment relationships and where unresolved responsibility
continues. Refinements serving the same goal remain within the same SPEC. A new
SPEC identifies a distinct design purpose and review boundary; it does not reset
the current product or turn an open quality gap into a completed result.

### Reading a structural report

Identify the supplied record and distinguish field/reference problems from theory
categories merely lacking a tag. Explain task-specific include/exclude/combine/split
or further research choices where consequential. Declared pass, waiver, missing
record and actual observed result remain distinct. Only the Agent selects the next
action using the professional method; the inspector neither recommends it nor
certifies research, readiness, correct design or task completion.


## When adopting important visual craft

Extend the relevant decision only as needed: intended perceptual relationship;
useful reuse scope; actual original-demo observation; selected source/variant and
rights; retained mechanism versus configuration or custom change; local fit with
real content; integrated-use result and remaining uncertainty. Functional
foundation, visual implementation and whole-product quality are different
responsibilities. Keep actual adopted locations in the current model and source
replacement reasons in meaningful revisions. No score, supplier list, candidate
quota or inspector status determines the professional choice.
