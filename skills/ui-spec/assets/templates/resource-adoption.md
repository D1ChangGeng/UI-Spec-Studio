# Resource adoption note

Use this optional note for a consequential choice, or record equivalent facts in existing project documentation.

## Outcome and constraints

User task, desired perception/behavior, accepted direction, runtime/content requirements.

## Selected starting point

Resource/item, original source, version or commit, implementation variant, demonstration configuration,
access method and observation date. Distinguish documented capability, inspected item and project evidence.
Link the viewed demonstration, relevant states/episode and rendering conditions.
Identify the observed layer and edited/demo/live-operation conditions. Connect the
design reference to this implementation resource, its visible value and intended placement.

## Judgment and reuse

Mechanism worth preserving, reuse level, fit and material tradeoff. Include existing/native alternatives
when they affected the decision. Explain which question further browsing resolved,
what remains uncertain and the specific gap requiring adaptation or custom work.

## Adaptation and ownership

Tokens, content, interaction and real data boundaries; modified files; dependencies and cleanup;
rights/required notices; local source or package update responsibility.

## Observed result

Actual viewports/content/states, input checks, combined runtime behavior, evidence references,
accepted scope and remaining observations. Keep project-specific choices in this project.
For changing resources, retain the trigger-to-result or cycle window, inspected
frames/video intervals and capture limits. Compare the source, combination and
delivered runtime separately; record how observation changed or confirmed the choice.
Re-answer the selection question in the runnable combination with current content
and corresponding states. Keep collected, actually examined and sufficient evidence distinct.
