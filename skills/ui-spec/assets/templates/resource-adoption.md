# Resource adoption note

Use this optional note for a consequential choice, or equivalent facts in existing documentation. Distinguish studied, compared, trialed and actually adopted sources; retain only details useful to the decision or maintenance.

## Outcome and constraints

User task, desired perception/behavior, accepted direction, runtime/content requirements.

Research question, target experience evidence and the uncertainty this resource
must resolve. Keep the current user's intent distinct from audience or product claims.

## Selected starting point

Resource/item, original source, version or commit, implementation variant, demonstration configuration,
access method and observation date. Distinguish documented capability, inspected item and project evidence.
Link the viewed demonstration, relevant states/episode and rendering conditions.
Identify the observed layer and edited/demo/live-operation conditions. Connect the
design reference to this implementation resource, its visible value and intended placement.

## Judgment and reuse

Visible strengths and likely perceptual effect at relevant scales; product fit, relationships
inherited together and material tradeoff. Explain how observation changed or confirmed selection.
Connect the quality target to the
actual package, copied source, configuration or asset carrying it. Scope behavior primitives and
visual foundations separately. Explain the concrete gap behind custom work and alternatives
actually assessed; research or design transfer alone does not establish implementation adoption.

For consequential alternatives, describe the material differences in composition,
type, material, interaction or time, along with comparison conditions and common
source lineage. Record evidence that challenged the first preference and why the
choice now fits; a source count alone cannot explain it.

## Local trial

Current fonts, language/content extremes, theme, container and interaction states;
trial source/entry and actually viewed evidence at intended scale and useful detail; preserved qualities, discovered gaps and
selection/adaptation decision before wider integration. Reuse existing representative evidence
where its conditions hold. State an inaccessible source or unexecuted trial precisely.

## Adaptation and ownership

Preserved layout/state/motion mechanisms; changed content, public configuration, theme,
composition or internals, with purpose and affected states. Actual implementation location;
data boundaries, dependencies, cleanup, rights/notices and update ownership. A substantial
mechanism rewrite carries its own validation responsibility.

## Observed result

Actual viewports/content/states, input checks, combined runtime behavior, evidence references,
accepted scope and remaining observations. Keep project-specific choices in this project.
For changing resources, retain the trigger-to-result or cycle window, inspected
frames/video intervals and capture limits. Compare the reference, original demo, local trial and
integrated journey at their own boundaries. Return from component detail to neighbors, page
hierarchy and the connected task to judge the adaptation's actual contribution.
Re-answer the selection question in the runnable combination with current content
and corresponding states. Keep collected, actually examined and sufficient evidence distinct.
