# Content and UX writing primary references

Reviewed for this method: **2026-10-25**. These sources document their own design systems and accessibility standards; their decisions inform candidate methods rather than prescribing one global brand voice or punctuation policy.

| Primary guidance | What it contributes | Application boundary |
|---|---|---|
| [GOV.UK — Understand content design](https://guidance.publishing.service.gov.uk/writing-to-gov-uk-standards/plan-manage-content/understand-content-design/) | Start from user needs, choose amount/format/place, keep content current | Use the reasoning across products; government-specific tone and publishing rules remain domain-specific |
| [GOV.UK — Identify user needs](https://guidance.publishing.service.gov.uk/writing-to-gov-uk-standards/plan-manage-content/identify-user-needs/) | Write needs and acceptance criteria from what people try to do | Actual audience evidence establishes user needs; examples illustrate the method |
| [Microsoft — UI writing style](https://learn.microsoft.com/en-us/windows/apps/design/style/writing-style) | Lead with important content, clear verbs, component/action text, error recovery, punctuation in context | Product voice comes from the current brand; Microsoft tone is a reference, not a required personality |
| [IBM Carbon — Content foundations](https://www.carbondesignsystem.com/building-blocks/foundations/content) | Terminology, capitalization, grammar, accessible product content and team-wide consistency | Inherit methods; IBM conventions apply when required by that product |
| [W3C WCAG 2.2 — Labels or instructions](https://www.w3.org/WAI/WCAG22/Understanding/labels-or-instructions) | Provide user-visible labels/instructions when input is expected | Actual control relationships and required accessibility semantics must still be checked in the implementation |
| [W3C WCAG 2.2 — Error identification](https://www.w3.org/WAI/WCAG22/Understanding/error-identification) | Identify erroneous input and describe the issue in text | Visual and programmatic delivery require separate validation |
| [Microsoft — UI text](https://learn.microsoft.com/en-us/windows/win32/uxguide/text-ui) | Work on content early; structure for scanning; organize instructions and supporting information | Platform-specific examples inform decisions rather than becoming fixed string-length laws |
| [Mailchimp — Voice and tone](https://styleguide.mailchimp.com/voice-and-tone/) | Separate stable brand voice from tone adapted to the user's situation | The distinction transfers; Mailchimp's humor and personality remain brand choices |
| [GOV.UK — Error message](https://design-system.service.gov.uk/components/error-message/) | Match input errors to fields, retain answers, explain recovery; distinguish service/permission conditions | Use the diagnostic distinction; GOV.UK's styling and summary pattern depend on the consuming design system |
| [W3C — Working with composite messages](https://www.w3.org/International/articles/composite-messages/) | Preserve context, complete meaning and reorderable variables in localization | Use the project's message format; shared source words alone do not justify sharing translated strings |
| [W3C — Text size in translation](https://www.w3.org/International/articles/article-text-size/) | Accommodate actual translation length through flexible containers and reflow | Historical examples explain variation; validate actual language strings rather than fixing a universal expansion ratio |
| [W3C — Chinese text layout requirements](https://www.w3.org/TR/clreq/) | Research punctuation, line breaking, Chinese/Western composition and type | Reviewed edition: 7 October 2026 Group Note Draft; an evolving layout reference, not a normative or finalized standard |
| [W3C WCAG 2.2 — Label in name](https://www.w3.org/WAI/WCAG22/Understanding/label-in-name.html) | Keep visible text labels within programmatic accessible names | The criterion applies to controls with visible text labels; icon-only controls still require appropriate accessible naming |
| [W3C WCAG 2.2 — Status messages](https://www.w3.org/WAI/WCAG22/Understanding/status-messages.html) | Expose status changes to assistive technology without requiring focus | Check actual semantics and announcement behavior; each state change need not interrupt the user |
| [W3C WCAG 2.2 — Text spacing](https://www.w3.org/WAI/WCAG22/Understanding/text-spacing.html) | Preserve content and function under user spacing overrides | The listed values are override conditions, not required author defaults; apply the language/script exception where relevant |
| [GOV.UK — Moderated usability testing](https://www.gov.uk/service-manual/user-research/using-moderated-usability-testing) | Observe plausible users completing credible tasks; avoid cues that reveal the intended path | Browser automation and editorial review establish different evidence from real-user comprehension |

Read the platform/design-system source matching the actual medium and product when a detailed convention matters. WCAG Understanding pages explain the corresponding criteria; [WCAG 2.2](https://www.w3.org/TR/WCAG22/) is the normative source. A selected check establishes its exercised behavior and scope. Research links and review dates identify external guidance; the current project controls business facts, product vocabulary, content approval and final localization.
