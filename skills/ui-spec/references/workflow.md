# Workflow: lead the work, preserve the design

## Operate on the current scope

The main path is `init → iterate → finish`; `audit` is available throughout. Optional `shape` resolves consequential uncertainty wherever it appears. These operations can be resumed or combined according to existing evidence. A request for one component refinement can complete one round; a fully approved product can enter real integration directly.

Use the common references as one professional foundation. The work below organizes their application rather than scheduling repeated file reads. Match effort to the task's impact, uncertainty, reversibility and available evidence.

## init — establish a useful working understanding

Read the actual project, supplied requirements, existing screens, approved design, dependencies, run/test commands and product maturity. Understand people, intended outcomes, content, platform and material business constraints. Find existing sources of design and task truth. Inventory available masters, asset rights and production capabilities alongside functional and design assets.

Identify the user-level product model, primary loop, result location, page families, core journeys and immediate gaps. Establish the requested redesign scope and separate preserved functional assets from visual candidates. Review explicit approval before inheriting a design. Start the design decision record with the observed facts and any high-impact open choices. Distinguish established facts from assumptions. Select the next useful increment and determine whether its direction is already clear or benefits from shape. Keep the working brief compact and linked to actual sources.

Initialization is sufficient when the agent can explain the task, preserve established constraints and choose a justified next action. For an implementation request, continue into shape or iterate in the same work session when feasible. A planning-only request ends with its requested decision support.

## shape — resolve just enough direction to build well

Use shape when the user requests exploration or an unresolved choice materially affects page responsibilities, visual identity or feasibility. Experienced users may supply part of the direction; complete the open parts. Users with only a goal receive an agent-led recommendation and an inspectable result.

1. **Frame the outcome.** Identify the user task, context, product facts, relevant content and success condition. Classify open questions as product, aesthetic, technical or consequential business uncertainty.
2. **Structure the experience.** Infer the primary interaction model from use, inspect comparable mature product flows and assess meaningful alternatives. Establish the responsibilities, meaningful entries/exits, key states and shared page family for the affected scope. Reuse the current journey map; include return, retry and recovery.
3. **Explore mature foundations.** Use the proposed product model to locate suitable complete pages, design systems or substantial blocks. Browse concrete candidates and their source; compare the design relationships, states and adaptation burden they supply. Let a strong candidate refine the initial hypothesis. Choose the highest appropriate reuse level before committing to a new composition.
4. **Form a direction.** Identify what the user needs to understand, then choose an organizing concept and suitable information/interaction representation. Relate hierarchy, density, typography, palette roles, imagery and motion to that concept. Identify load-bearing visual assets and their intended roles; compare material and production routes early enough to influence the composition. Use established brand choices as constraints. When direction is open, read relevant references for their mechanisms and form a coherent recommendation.
5. **Check implementation fit.** Before locking the major layout or treatment, connect product-pattern evidence with external implementation research. Assess incumbent visual candidates against the same target as external work. Build a surface-by-element shortlist with concrete sources, expected effects and reuse depth. Proactively explore both required capabilities and better expressive possibilities. Use the resource catalog as an open starting map. Compare exact items, demos/configurations and reuse levels with the product direction, content availability and material service constraints. Read integration guidance when authority, persistence or real business behavior affects the design. Explore high-impact technical uncertainty with a small probe.
6. **Make the important choice inspectable.** Build a representative composition or interaction where rendering will resolve uncertainty. Compare a small number of genuinely different alternatives only when the comparison can change the choice. Keep experiments within the smallest useful scope.
7. **Carry a usable decision forward.** Apply the consequential-direction check: obtain user choice when credible, unresolved alternatives materially alter the experience; proceed under clear intent or explicit delegation. Record the selected or provisional direction, rationale, decision authority, inherited constraints, remaining questions and next increment. Continue implementation when the user's scope permits it. Seek review of significant direction choices using the actual result.

Shape ends when there is enough grounded direction for the next useful increment. Later findings can reopen the affected decision. A well-supported choice remains adjustable; uncertainty alone does not require a larger questionnaire or a fixed set of alternatives.

## iterate — deliver one meaningful increment

**Orient and choose.** Reconcile the user's latest feedback with accepted decisions, current code, incomplete journeys and outstanding findings. A simple request to continue is enough: choose the next valuable increment and state its intended outcome briefly.

**Define the slice.** Identify affected pages/states, shared dependencies, the user outcome and review conditions. Prefer an end-to-end task or coherent family when the relationships matter. Establish what will be observable at the end of this round.

**Design and select.** Confirm that the product interaction model and visual direction are settled for this scope, or keep the round a bounded direction probe. Present the consequential choices with concrete sources before broad implementation. Apply design theory to concrete foundation candidates, then carry the selected hierarchy, proportions, type rhythm and state relationships into the increment. Connect content meaning to an expression concept, a representation and concrete visual/interaction grammar. Apply the analysis lenses and visual principles. Source load-bearing assets early and choose the appropriate medium. Carry forward proven, suitable choices. Proactively explore relevant ecosystem work for substantive new needs and meaningful opportunities. Pair the selected demo with its exact source/configuration, compare total cost, and decide direct adoption, adaptation, composition, technique transfer or original implementation. Use optional shape to resolve a material direction question; keep familiar parts moving.

**Implement.** Acquire, adapt or produce the selected visual material, retaining its source, editable controls and required derivatives. Match static, timed or real-time delivery to the actual task and available tools. Work in the existing project. Adapt the selected foundation at its useful granularity and preserve its valuable relationships. Use representative short, typical and long content, realistic data density and meaningful state changes. Keep fixture values identifiable and real product claims evidence-based. Structure data boundaries so accepted components can later use real services. Preserve selected resource mechanisms and provenance while adapting tokens, content, behavior and runtime ownership. Resolve the highest-impact selection uncertainty in a small representative integration.

**Inspect and correct.** Inspect whole-surface meaning, structural relationships and details against the intended craft target. Run actual UI paths and inspect real viewport captures. Review affected cross-page anchors, states and variants. Inspect the delivered assets at their actual sizes and placements, then check reused parts together for semantic behavior, style/layer conflicts, attention competition, runtime cost and cleanup. Include asset loading/failure, theme/crop and quiet states where relevant. Diagnose the responsible layer, repair it and recheck the impacted scope. End a round when its task is coherent, its required evidence exists and it is ready for the user's judgment.

**Present and continue.** Provide the working entry and the updated design decision record together. Show which sources shaped each important surface, how they were used, where the implementation lives, and what was observed. Relate the resulting primary action and continuing task to the selected product model. Present unresolved high-impact choices explicitly, then state the inspected scope and next recommended increment. Record explicit approval already supplied for a clear scope. Preserve open review items. User feedback guides the next round without requiring the user to restate common principles.

### Turn subjective feedback into a useful repair

Treat a user's observation as evidence of an experience to investigate. A proposed implementation is one candidate unless explicitly required. For “too large,” compare control scale, composition occupancy, preview scaling and whitespace. For “jumps when switching,” examine shared anchors, scroll restoration, component identity and transition timing.

State the most likely explanation after inspecting the result, use a bounded change to test it, and compare the new render. Promote a correction into shared rules when it applies across the family. Preserve local specificity where it belongs to one surface.

## audit — inspect an identified scope

Match review-only versus repair authorization. Reconcile the scope with routes, navigation, roles, overlays and actual task paths. Inspect whole-product structure, page families and then local details. Use the verification reference for coverage and evidence.

A finding connects an observed result to user impact, the relevant principle, likely cause and repair scope. Shared issues receive shared fixes and related-page checks. Report inspected coverage separately from the complete inventory. Preserve the distinction between pending, blocked, failed and approved exceptions.

## finish — complete real connection work

Read the integration reference and use its six-part flow: **reconcile → contract → sequence → connect → verify → deliver**.

Confirm the accepted product model, reference-informed design and resource map from existing approval. Preserve the chosen primary action and continuation while translating the mapped implementations into real behavior. Compare it with actual services, data, permissions and code. Resolve the missing behavior at its real owner, connect complete user tasks, and regress both design and product outcomes. Common visual and UX principles continue to apply to real data, errors and asynchronous states. Carry asset masters, export settings, delivery variants, rights and measured runtime/fallback conditions into the handover. Carry resource configuration, attribution and modification ownership into the product; verify controlled state, delayed responses and combined runtime behavior at the real boundary.

A material change to accepted appearance, task meaning or user commitment returns the affected scope for review. Continue independent integration while that decision is pending. Deployment or real-world actions follow the applicable authorization; a local, static or service-backed product finishes against its own actual boundary.

## Continuity with lightweight records

Prefer existing project documents and tests. A useful minimal record contains the accepted direction, current outcome, shared constraints, component decisions worth reusing, review scope, evidence and next priority. Store route details close to their implementation where practical.

The optional `.ui-spec` manifest records declared coverage, scoped approval and real connection evidence. Its `phase` identifies the active operation. Different scopes can have different maturity within one project. Use the existing task system or scoped records to express that difference.

Preserve one current implementation and its Git history. Evidence references identify reviewed conditions. Update reusable knowledge once at its authoritative location. The host owns session persistence and context management; these project records supply sources an agent can read when needed.

## Apply the practice to the actual medium

A README, publication, chart, slide or visual explanation can use the same understanding → expression → realization → observation loop. Identify its reading or interaction task, host constraints and actual deliverable. Keep the workflow proportionate: a static document can finish through valid content, working links, editable assets and rendered publication checks. A live product additionally requires its real state and service boundaries.

Keep design reasoning and execution connected without producing a document at every intermediate step. A brief causal record for a significant choice is enough. Use small representative probes for uncertainty; extend an established direction directly. Improve the reusable method when warranted while preserving current project choices and host responsibilities.
