# Workflow: lead the work, preserve the design

## Operate on the current scope

The main path is `init → iterate → finish`; `audit` is available throughout. Optional `shape` resolves consequential uncertainty wherever it appears. These operations can be resumed or combined according to existing evidence. A request for one component refinement can complete one round; a fully approved product can enter real integration directly.

Organize each operation around Product UI Experience Alignment: target experience, mature evidence, chosen inheritance/adaptation and actual-use verification. Use the common references as one foundation; apply exploration wherever evidence can change a decision. Match effort to impact, uncertainty and reversibility.

## init — establish a useful working understanding

Read requirements, code, screens, approved design, dependencies and run/test commands. Establish people, outcomes, product maturity, content/locale ownership, roles, growth and device/network conditions. Inspect the current scope with available browser, image and temporal tools; note unobserved conditions, asset masters, rights and production capabilities.

Identify the primary loop, result location, page families, journeys and gaps. Expand a named reference into the relevant product/page/flow/quality; otherwise find mature task-level and local references proactively. Preserve functional contracts and assess visual candidates against the target. Record observed facts, approval, assumptions and consequential questions compactly. Choose a useful increment and whether shape would resolve its direction.

Initialization is sufficient when the agent can explain the task, preserve established constraints and choose a justified next action. For an implementation request, continue into shape or iterate in the same work session when feasible. A planning-only request ends with its requested decision support.

## shape — resolve just enough direction to build well

Use shape when the user requests exploration or an unresolved choice materially affects page responsibilities, visual identity or feasibility. Experienced users may supply part of the direction; complete the open parts. Users with only a goal receive an agent-led recommendation and an inspectable result.

1. **Frame the outcome.** Establish task, context, product facts, content authority, language and success. Classify uncertainty as product, aesthetic, technical or consequential business questions.
2. **Structure the experience.** Infer the interaction model, inspect comparable flows and assess meaningful alternatives. Reuse the journey map; establish affected responsibilities, entries/exits, key states, shared family and return/recovery paths.
3. **Explore mature foundations.** Turn important parts, states and relationships into research questions. Locate complete pages, systems or blocks and follow relevant clues through playback, scrolling, switching and operation. Distinguish carrier, player, application and displayed content. Compare actual relationships and meaningful temporal episodes, refine the search from discoveries, and choose the highest appropriate reuse level.
4. **Form a direction.** Assign needed understanding to content roles and decision-time placement. Choose an organizing concept, representation, product voice and state-aware tone. Coordinate hierarchy, density, type, color, assets and motion with accepted identity. Study load-bearing material and production routes while composition can change. Explain transferable relationships and their conditions.
5. **Check implementation fit.** Connect design-reference evidence to concrete implementation candidates, assessing internal work against the same target. Compare exact items, demo settings, reuse depth, expected effects and adaptation cost. Use the catalog as an open discovery map. Read integration guidance when authority, persistence or real behavior affects design; probe consequential technical uncertainty.
6. **Make the choice inspectable.** Build the smallest representative composition or interaction that can resolve uncertainty. Compare meaningful alternatives under suitable content density, display size and event phases. Show the observed difference and product consequence.
7. **Carry a usable decision forward.** Seek a user choice for unresolved alternatives that materially alter direction; proceed under clear intent or delegation. Record selected/provisional direction, rationale, authority, inherited constraints and remaining questions with the result. Continue implementation within the requested scope.

For repeated or asynchronous tasks, examine the execution path while selecting the interaction: what is prepared on entry, requested on intent, shown immediately and confirmed later. Compare preparation cost, freshness and side effects before choosing preloading, parallel work or caching. For frequently maintained content, establish source ownership, reusable defaults, meaningful overrides and the operator's actual selection/recovery path. These judgments can change the design before broad implementation.

Shape ends when the main target, important parts/states, consequential temporal relationships and implementation path have sufficient evidence. Carry remaining questions into the next increment; new findings can reopen a choice. Explore by decision value rather than a fixed source count.

## iterate — deliver one meaningful increment

**Orient and choose.** Reconcile the user's latest feedback with accepted decisions, current code, incomplete journeys and outstanding findings. A simple request to continue is enough: choose the next valuable increment and state its intended outcome briefly.

**Define the slice.** Identify affected pages/states, shared dependencies, the user outcome and review conditions. Prefer an end-to-end task or coherent family when the relationships matter. Establish what will be observable at the end of this round.

**Design and select.** Establish the interaction model and visual direction for this scope, or keep it a bounded probe. Show consequential choices with actual references before broad implementation. Apply the analysis and visual principles to foundation candidates; preserve suitable existing decisions. Explore new needs and useful opportunities, following high-value clues. Connect content meaning to representation, language and visual grammar; source defining assets early. Pair selected demos with exact sources/settings, compare total cost and choose adoption, adaptation, composition, technique transfer or purposeful original work. Use optional shape for material direction questions while familiar work continues.

**Implement.** Work in the existing project. Adapt the chosen foundation at its useful scope; retain mechanisms, provenance and editable controls. Acquire or produce material and derivatives using suitable static, timed or real-time delivery. Compose actual or identified fixture strings, realistic data density, locales and state changes with type, layout and assets. Include short/typical/long content; keep product claims grounded. Adapt tokens, behavior and runtime ownership with data boundaries that can connect to real services. First resolve the most consequential uncertainty in a runnable task slice.

**Inspect and correct.** Revisit the research questions in the runnable result under comparable scale, content density, state and pace. Inspect whole composition, relationships, detail, actual tasks, continuous episodes and related views. Check anchors, copy/locales, assets and combined semantics, layers, attention, loading/failure and quiet states. Distinguish visible phenomenon, interpretation and suspected cause; investigate, repair and recheck. Expand the slice when evidence supports its fit; reopen selection when the relationship fails. End with a coherent task and examined evidence.

When the slice concerns performance or operating work, observe its complete sequence: repeated input, usable result, confirmed completion and recovery. Compare changes under named conditions using appropriate task measurements. Inspect motion across time, scroll position under content growth, and the effective content after shared or individual updates. Keep changes to perceived feedback, actual task duration and resource consumption distinguishable.

**Present and continue.** Provide the working entry and current decisions, including consequential copy and its authority. Link important choices to the source candidate, perceptible reason, actual implementation and inspected result; use comparable frames or event intervals when they clarify a change. Relate the action and continuation to the product model. State unresolved high-impact choices, observed conditions and the next increment. Record existing scoped approval and open items. User feedback guides continuation without restating common principles.

### Turn subjective feedback into a useful repair

Treat a user's observation as evidence of an experience to investigate. A proposed implementation is one candidate unless explicitly required. For “too large,” compare control scale, composition occupancy, preview scaling and whitespace. For “jumps when switching,” examine shared anchors, scroll restoration, component identity and transition timing.

State the most likely explanation after inspecting the result, use a bounded change to test it, and compare the new render. Promote a correction into shared rules when it applies across the family. Preserve local specificity where it belongs to one surface.

## audit — inspect an identified scope

Match review-only versus repair authorization. Reconcile the scope with routes, navigation, roles, overlays and actual task paths. Inspect whole-product structure, page families and then local details. Use the verification reference for coverage and evidence.

A finding connects an observed frame or interval to perceptual/task impact, the relevant principle, a cause to investigate and repair scope. Use the nine experience dimensions to locate missing responsibilities. Shared issues receive shared fixes and related-page/sequence checks. Report actually viewed coverage separately from recorded media and the full inventory. Preserve pending, blocked, failed and approved-exception meanings.

## finish — complete real connection work

Read the integration reference and use its six-part flow: **reconcile → contract → sequence → connect → verify → deliver**.

Confirm the accepted product model, reference-informed design and resource map from existing approval. Preserve the chosen primary action and continuation while translating the mapped implementations into real behavior. Compare it with actual services, data, permissions and code. Resolve the missing behavior at its real owner, connect complete user tasks, and regress both design and product outcomes. Common visual and UX principles continue to apply to real data, errors and asynchronous states. Carry asset masters, export settings, delivery variants, rights and measured runtime/fallback conditions into the handover. Carry resource configuration, attribution and modification ownership into the product; verify controlled state, delayed responses and combined runtime behavior at the real boundary.

Connect source-owned content, localization and operational changes to the same outcomes shown by the UI. Validate freshness, permissions, duplicate actions, partial completion and unknown results when applicable. Explain which runtime and maintenance conditions have been observed and where the authoritative source can be updated.

A material change to accepted appearance, task meaning or user commitment returns the affected scope for review. Continue independent integration while that decision is pending. Deployment or real-world actions follow the applicable authorization; a local, static or service-backed product finishes against its own actual boundary.

## Continuity with lightweight records

Use existing project records for accepted direction, current outcome, shared rules, reusable component decisions, reviewed conditions and next priority. The optional `.ui-spec` manifest records declared coverage, scoped approval and connection evidence; its phase describes current work while individual scopes retain their own maturity. Keep one current implementation with Git history and update decisions at their authoritative location. These records supply readable evidence; the host owns session persistence and context management.

## Apply the practice to the actual medium

A README, chart, slide or visual explanation uses the same understanding → expression → realization → observation loop with its own reading task and host constraints. A static document finishes through valid content, working links, editable assets and rendered publication checks; a live product also requires its state and service boundaries. Record significant causes and decisions compactly. Probe uncertainty where it can change the result, extend established direction directly, and preserve project choices when improving reusable methods.
